# 01 · 从引擎到文字：`Instance`、继承、虚函数和成员赋值

![从引擎创建到文字绘制](./图片/01-调用链.svg)

## 1. `Instance` 到底是什么

源码的 `blender::draw::overlay::Instance` 是 Overlay **绘制引擎对象**，不是几何节点的“实例域”。它声明为 `class Instance : public DrawEngine`，见 `source/blender/draw/engines/overlay/overlay_instance.hh:57`。`public` 继承表示它是一个 `DrawEngine`，可以经由 `DrawEngine *` 或 `DrawEngine &` 被绘制管理器调度。

基类 `DrawEngine` 在 `source/blender/draw/intern/DRW_render.hh:71–133`。它把引擎生命周期抽象成 `init()`、`begin_sync()`、`object_sync()`、`end_sync()` 和 `draw()` 等虚函数。`= 0` 是纯虚函数，基类不提供实际绘制流程；派生类必须实现。`Instance` 的相关声明带 `final`，说明覆盖了基类虚函数且禁止进一步覆盖。**`update_text_depth()` 只是 `Instance` 的私有普通成员函数，没有 `virtual`，没有基类版本。**

基类析构函数是 `virtual ~DrawEngine() = default`。这使 `DrawEngine::Pointer` 通过基类指针执行 `delete instance` 时，会正确调用 `Instance::~Instance()`，随后销毁基类部分。`Instance` 析构函数在 `overlay_instance.hh:120–126`，负责销毁文字缓存和深度缓存。

## 2. 对象是哪里创建的

`DrawEngine::Pointer::set_used(true)` 在 `instance == nullptr` 时调用虚函数 `create_instance()`。Overlay 的 `Engine::create_instance()` 在 `source/blender/draw/engines/overlay/overlay_engine.cc:17–20` 中返回 `new Instance()`。`new` 创建真实的 `overlay::Instance`；返回类型是 `DrawEngine *`，因此管理器可以通过共同基类保存不同引擎。

管理器在同步时通过 `DrawEngine &instance` 调用 `instance.init()`、`instance.begin_sync()` 等，见 `source/blender/draw/intern/draw_context.cc:1088–1101`。这些调用经过虚函数机制进入 Overlay 的实现。随后 `Instance::draw()` 内部选择 3D 视图路径 `draw_v3d()`；`draw_v3d()` 直接调用本章的 `update_text_depth()`，见 `overlay_instance.cc:938–939`。

所以调度层级是：

```text
DrawEngine 虚接口
  → 实际对象 overlay::Instance
  → Instance::draw() 普通函数体
  → Instance::draw_v3d() 普通成员函数
  → Instance::update_text_depth() 普通成员函数
```

## 3. `Instance` 的成员在哪里初始化

`overlay_instance.hh:61–70` 声明 `ViewDepths *text_depth_cache_ = nullptr;` 和 `State state;`。前者在构造对象时为空；后者是**直接嵌在 `Instance` 对象中的成员**，不是另外 `new` 出来的对象，也不通过基类继承。`State` 自身的字段大多有类内初始值，见 `overlay_private.hh:128–185`。

`Instance::init()` 在 `overlay_instance.cc:21–145` 开始，从 `DRW_context_get()` 获取当前绘制上下文并填充 `state`。例如：

```cpp
state.region = ctx->region; // 当前屏幕区域
state.v3d = ctx->v3d;       // 当前 3D 视图设置；可能为空
state.space_type = state.v3d != nullptr ? SPACE_VIEW3D :
                   eSpace_Type(ctx->space_data->spacetype);
```

`state.show_text` 在 `init()` 开始先被设为 `false`。如果当前是 3D 视图、Overlay 未隐藏，则进一步根据是否选择绘制、是否只绘制深度和用户是否隐藏文本计算，见 `overlay_instance.cc:89–95`。因此它表达“这一轮是否显示文字”，不等于“至少有一条文字需要深度测试”。

`state.is_space_v3d()` 位于 `overlay_private.hh:218–221`，实现只有 `return this->space_type == SPACE_VIEW3D;`。它没有虚函数，也不查 GPU。`this` 指当前的 `State` 对象；末尾 `const` 约束函数不修改该对象。

## 4. `state.dt` 在哪里创建

`State` 中的 `DRWTextStore *dt = nullptr` 声明于 `overlay_private.hh:137`。每次 `Instance::begin_sync()` 都执行：

```cpp
DRW_text_cache_destroy(state.dt);
state.dt = DRW_text_cache_create();
```

见 `overlay_instance.cc:455–463`。`DRW_text_cache_create()` 使用 `MEM_new<DRWTextStore>` 创建新的文字存储对象，定义在 `draw_manager_text.cc:79–82`；`destroy` 接受空指针，非空时用 `MEM_delete` 销毁，见 `84–90`。因此第一次 `begin_sync()` 的 `nullptr` 是合法的。

`DRWTextStore` 在 `draw_manager_text.cc:68–77` 定义：`cache_strings` 存待画文字，`string_allocator` 保存某些字符串内容，`const ViewDepths *depths` 初始为空。它是普通 `struct`，没有这里相关的继承或虚函数。属性文本的值、锚点与标志会在同步阶段加入 `cache_strings`。

`DRW_text_cache_needs_depth_test()` 遍历这个数组，发现任一条文字含 `DRW_TEXT_CACHE_OCCLUSION_CULLING` 标志即返回真，见 `draw_manager_text.cc:342–350`。这一函数回答“要不要准备一整张深度图”，不会逐条判断可见性。

## 5. 谁画文字，谁释放数据

`Instance::draw_v3d()` 在深度预处理之后调用 `update_text_depth()`，随后更晚调用 `draw_text()`。`draw_text()` 绑定颜色帧缓冲，关闭 GPU 深度测试并调用 `DRW_text_cache_draw(state.dt, state.region, state.v3d)`，见 `overlay_instance.cc:1055–1063`。`DRW_text_cache_draw()` 再对每条文字投影锚点、按需比较 CPU 深度并决定是否画字，见 `draw_manager_text.cc:244–301`。

`DRWTextStore::depths` 只借用指针。所有权留在 `Instance::text_depth_cache_`。`Instance::~Instance()` 销毁两个缓存；因为 `DrawEngine` 析构函数是虚函数，经基类指针删除时也会执行这个清理。下一篇将逐行解释这些指针何时赋值、何时失效。
