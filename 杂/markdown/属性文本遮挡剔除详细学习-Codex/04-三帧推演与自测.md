# 04 · 三帧推演、所有权与自测题

![三个连续帧](./图片/04-三帧缓存.svg)

## 1. 连续三帧逐步推演

**帧 N：**视口 1000×800，相机 A，存在请求遮挡测试的文字。`begin_sync()` 建立本轮 `DRWTextStore`；`update_text_depth()` 首次分配 `ViewDepths` 与 CPU 像素数组，从 GPU 读取 A 的当前深度；`DRWTextStore` 借用它；`draw_text()` 按 A 的投影逐条比较并绘制。

**帧 N+1：**视口仍为 1000×800，相机转到 B。文字清单在新一轮 `begin_sync()` 中重建。深度缓存尺寸仍匹配，四参数 `GPU_texture_read` 将 B 的**当前帧**深度覆写进原 CPU 数组。新文字锚点按 B 投影，与 B 的深度比较。缓存地址可不变，但像素内容必须变。

**帧 N+2：**视口改为 1200×800。旧 `ViewDepths::w/h` 不匹配，先释放旧结构体和数组，再建立新的并回读。如果用户随后关闭相关显示或不再有任何文字要求遮挡测试，下次调用会先清空借用指针，再释放 CPU 深度缓存，最后返回。

## 2. 四种资源不要混在一起

![四种对象及所有权](./图片/02-所有权.svg)

| 对象 | 创建/赋值 | 拥有者 | 释放位置 |
|---|---|---|---|
| `overlay::Instance` | `Engine::create_instance()` 返回 `new Instance()` | `DrawEngine::Pointer` | `free_instance()` 经虚析构删除 |
| `state.dt` 指向的 `DRWTextStore` | `begin_sync()` 中 `DRW_text_cache_create()` | `Instance` | 下一轮 `begin_sync()` 或析构 |
| `text_depth_cache_` 及其 CPU 数组 | 首次 `update_text_depth()` 回读 | `Instance` | 不再需要、尺寸变化或析构 |
| `GPUViewport::depth_tx` | 视口资源创建路径 | GPU 视口系统 | 视口资源清理 |

`DRWTextStore::depths` 是借用指针，不在上述所有权清单中另占一份资源。它与 `text_depth_cache_` 可以同时指向**同一个** `ViewDepths` 对象。

## 3. 自测：能否独立回答

1. 若 `state.show_text == false`，`DRW_text_cache_needs_depth_test()` 是否会被调用？提示：C++ `||` 的短路求值。
2. 若相机转动但视口尺寸不变，会执行哪个 `GPU_texture_read` 重载？旧像素是否仍然用于比较？
3. 若窗口由 800×600 变为 600×800，像素总数相同，可以复用旧数组吗？提示：考虑 `y * w + x`。
4. `GPU_viewport_depth_texture()` 返回的纹理由谁释放？`ED_view3d_depths_free()` 是否会释放它？
5. 如果通过 `DrawEngine *` 删除 Overlay `Instance`，为什么 `Instance` 的清理代码仍会运行？
6. `update_text_depth()` 返回 `void`，结果怎样到达 `DRW_text_cache_draw()`？

### 核对答案

1. 不会；第一个条件已经为真，后续条件无需求值。
2. 四参数版本；它覆写原 CPU 数组，内容成为相机新视角的深度。
3. 不能；尺寸对不上会触发重建，且行跨度不同。
4. GPU 视口系统；`ED_view3d_depths_free()` 只释放 CPU `ViewDepths` 和内部数组。
5. `DrawEngine` 析构函数是虚函数。
6. 本函数调用 `DRW_text_cache_depth_set(state.dt, text_depth_cache_)`，将借用指针保存在 `DRWTextStore` 中；后续绘制读取该字段。

## 4. 一句话复述整个实现

Overlay 引擎的虚函数入口组织每轮同步与绘制；普通成员函数 `update_text_depth()` 在正确的绘制时刻把 GPU 当前深度读进 `Instance` 拥有的 CPU 数组，按需要重建或复用该数组，把只读指针借给当前轮 `DRWTextStore`，随后文字绘制代码逐条使用它判断可见性。
