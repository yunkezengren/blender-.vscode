0一图总览

与 VectorSet 的根本差异只有一条：键和值都住在槽里——没有 keys_ 数组、没有"第 i 个"、没有末尾补位。一张槽表就是容器的全部。

Map 对象头
4 标量 + 内联槽缓冲		 ─→ slots_ 槽表（唯一容器）
每槽 = 状态 + Key + Value

查找路径：hash(key) → 探测 → 命中槽 → 槽内直接取 value（无需二次跳转）。遍历序 = 槽位序（哈希决定，不确定）。

2槽逐字节：SimpleMapSlot（默认槽型）

BLI_map_slots.hh L48-L57。8 槽实例：hash(A)→0、hash(B)→2、hash(C)→5，"X" 曾占 #1 后被删。

三行读法：① state_ 是独立 uint8 枚举（0 空 / 1 占 / 2 删）——不像 VectorSet 复用 int64 符号；② 键值并排躺在同一槽内，命中即取，无二次寻址；③ 墓碑槽（#1）的键值缓冲是已析构的未定义内存——槽类型约定"非占用态视为 trivially destructible"，不保证清零。
澄清一个常见误传（含我自己此前讲错的）：槽里不存哈希副本（无 stored_hash_ 字段，occupy 的 hash 参数仅用于探测定位）。存哈希副本的路线在本仓库的并发容器（BLI_concurrent_map）里，不在 Map 主线。

4增 / 删动线

add_new(key, value)——五步（与 VectorSet 前四步同构）

① 容量检查ensure_can_add
负载 1/2 同款
② 算哈希hash_(key)
可换异型键（_as 后缀）
③ 探测墓碑跳过/空槽停
共享 BLI_hash_tables 底座
④ 槽内构造placement new key+value
没有 keys_ 追加这一步
⑤ state_=Occupied
无下标可记（VectorSet 记 index）

remove_contained(key)——两行完事（BLI_map.hh L387-394）

① slot.remove()state_→Removed
值析构、键留哨兵/枚举
② removed_slots_++
仅此而已——无补位、无改槽

对比 VectorSet 的三步（补位 + 沿链改下标 + 留墓碑）：单容器路线没有下标要维护，这是它意外的简洁红利。代价就是遍历序哈希化。

5增长时间线与内存账（Key=int, Value=float）

元素数槽 total槽表占用内联？堆分配
1-488 × ~12B ≈ 96B✅ 零堆0
51616 × ~12B ≈ 192B❌ 槽表转堆1 次
932≈384B❌再 1 次

对照 VectorSet 同规模：槽 8B/个但另有 keys_ 数组。小键小值时 Map 更省（无二次寻址、槽内直达）；键值变大（≥100B）时 Map 更早放弃内联——内联门槛公式按 K+V 之和计算。
