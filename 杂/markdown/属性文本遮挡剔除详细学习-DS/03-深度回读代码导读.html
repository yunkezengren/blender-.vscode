00本册定位与阅读路径

遮挡剔除的完整链路是「锚点前移 → 深度回读 → 投影比较 → 剔除判定」。 第 2 册讲了投影与深度比较（绘制时发生），本册讲解更早的一步： 场景深度缓冲如何在正确的时机、以最低的开销从 GPU 搬到 CPU。 这一步由 Instance::update_text_depth() 独立承担，代码只有 37 行， 却牵涉四个子系统：窗口管理器（视口）、GPU 封装层（纹理回读）、编辑器（ViewDepths）、绘制层（文本缓存）。

阅读路径：

  • 只想看懂函数 → 按 §1 → §2 顺序读即可。
  • 想知道每个类型 / API 的来龙去脉 → 跳到 §3 类型与 API 手册。
  • 好奇「为什么不每帧都无脑回读」 → §4 关键设计决策。
  • 要改这段代码 → 直接读 §6 修改指南。
前情 锚点为什么要沿视线前移（点云 §213–225、实例 §240–265）见本系列对 overlay_attribute_text.hh 的讲解； 锚点深度与场景深度如何比较见第 2 册。

01函数在帧渲染中的时序

1.1 一帧内的调用位置

update_text_depth() 在覆盖层引擎的 draw_viewport() 中被调用一次 （overlay_instance.cc:939），位于深度预通道完成之后、 网格与坐标轴绘制之前：

draw_viewport()overlay_instance.cc · 每帧执行一次
▼① prepass：场景几何写入深度缓冲（GPU）
update_text_depth() · 939 行← 本册：此刻回读，深度仍是「纯场景」
▼② grid / axes 等覆盖层绘制，往深度缓冲写入自己的单像素深度
▼③ draw_text() · 1009 行 → DRW_text_cache_draw()
投影 + 逐文本深度比较消费刚回读的 CPU 深度数组

函数开头的注释正是对这一时点的声明：

1.2 为什么时点不能移动

深度比较的对象是「场景几何」——物体表面。视口深度缓冲在整帧内被多次写入：

  • prepass 之后：只有场景几何，深度值就是「遮挡表面」——正确时点
  • grid / axes 之后：网格线、坐标轴也写入了各自的深度（虽然是单像素）， 若文本锚点恰好落在网格线上方，会被自己的辅助线「遮挡」——污染
  • prepass 之前：深度缓冲可能还是上一帧的残留或清空值——错误数据
!

调用点的注释同样强调了这一点

调用处（938 行）写着 /* Read scene depth before the grid and axes write their own one-pixel depth. */。 两个注释一脉相承：函数体注释声明「回读发生在 prepass 后」，调用点注释声明「必须在网格/坐标轴污染前」。

02逐行拆解

先看完整函数，然后逐段拆解：

overlay_instance.cc : 1017 – 1053 · 完整函数
void Instance::update_text_depth()
{
  if (!state.show_text || !state.is_space_v3d() || !DRW_text_cache_needs_depth_test(state.dt)) {
    DRW_text_cache_depth_set(state.dt, nullptr);
    if (text_depth_cache_ != nullptr) {
      ED_view3d_depths_free(text_depth_cache_);
      text_depth_cache_ = nullptr;
    }
    return;
  }
  /* Refresh from this frame after the depth prepass, before grid and axes can alter depth.
   * The read-back is deliberately skipped when no text requested occlusion testing. */
  GPUViewport *viewport = WM_draw_region_get_viewport(const_cast<ARegion *>(state.region));
  gpu::Texture *depth_tx = GPU_viewport_depth_texture(viewport);
  const int width = GPU_texture_width(depth_tx);
  const int height = GPU_texture_height(depth_tx);
  if (text_depth_cache_ != nullptr &&
      (text_depth_cache_->w != width || text_depth_cache_->h != height))
  {
    ED_view3d_depths_free(text_depth_cache_);
    text_depth_cache_ = nullptr;
  }
  if (text_depth_cache_ == nullptr) {
    text_depth_cache_ = MEM_new_zeroed<ViewDepths>("ViewDepths");
    text_depth_cache_->w = width;
    text_depth_cache_->h = height;
    text_depth_cache_->depths = static_cast<float *>(
        GPU_texture_read(depth_tx, GPU_DATA_FLOAT, 0));
    text_depth_cache_->depth_range[0] = 0.0;
    text_depth_cache_->depth_range[1] = 1.0;
  }
  else {
    /* Refresh the contents with this frame's depth. */
    GPU_texture_read(depth_tx, GPU_DATA_FLOAT, 0, text_depth_cache_->depths);
  }
  DRW_text_cache_depth_set(state.dt, text_depth_cache_);
}

三个条件任一为真就整段跳过，且必须顺手清理：

条件含义为什么要早退
!state.show_text 用户关闭了「显示叠加文本」（覆盖层设置里的 Text 开关） 根本不会绘制文本，深度无人消费
!state.is_space_v3d() 当前空间不是 3D 视口（覆盖层引擎理论上只在 V3D 运行，这是防御） 没有 RegionView3D，投影与深度比较无意义
!DRW_text_cache_needs_depth_test() 本帧没有任何一条缓存文本带 DRW_TEXT_CACHE_OCCLUSION_CULLING 标志 性能核心：回读昂贵（见 §4.1），无人申请就不做

早退分支做两件事：把借用指针置空（depth_set(dt, nullptr)， 防止消费端拿到即将释放的悬垂指针）和释放自有缓存（避免尺寸/场景变化期间白白持有数 MB 内存）。 注意顺序：先置空借用、再释放、最后才置空自有指针——释放后 text_depth_cache_ = nullptr 保证下一帧从「分配」分支重新开始。

i

flags 是在哪个阶段写入的？

DRW_TEXT_CACHE_OCCLUSION_CULLING 在覆盖层引擎收集文本时打上 （overlay_attribute_text.hh 的 text_flag_，经 add_text_to_cache() 传入 DRW_text_cache_add）。所以当 update_text_depth() 在 939 行执行时， 本帧的文本缓存已经填充完毕，探测结果是准确的。

2.2 取视口与深度纹理 1029–1032

overlay_instance.cc : 1029 – 1032
GPUViewport *viewport = WM_draw_region_get_viewport(const_cast<ARegion *>(state.region));
gpu::Texture *depth_tx = GPU_viewport_depth_texture(viewport);
const int width = GPU_texture_width(depth_tx);
const int height = GPU_texture_height(depth_tx);

两级获取链：区域 → 视口 → 深度纹理。 Blender 的每个 ARegion（窗口内的一个区域）在绘制时持有一个 GPUViewport—— GPU 侧的「画布」，内含颜色纹理、叠加纹理和一张深度纹理 depth_tx。 这张深度纹理正是 prepass 写入的目标，也是本函数要回读的数据源。 宽高从纹理本身读取而非 region->winx/winy，保证与回读出的数组尺寸严格一致 （视口分辨率可能与区域像素尺寸有缩放差异）。

这两个函数都是纯 getter，实现只有一行：

跨帧复用的缓存只在一种情况下报废：视口尺寸变了（用户拉伸了窗口、 改变了区域布局、缩放系数变化）。此时旧数组 w × h 与新帧不匹配， 继续写入会越界，必须释放重建。 尺寸没变则走 §2.5 的原地刷新路径——不释放、不重新分配。

2.4 分配新缓存 1039–1047

overlay_instance.cc : 1039 – 1047 · 首帧或尺寸变化后
if (text_depth_cache_ == nullptr) {

  text_depth_cache_->h = height;

      GPU_texture_read(depth_tx, GPU_DATA_FLOAT, 0));
  text_depth_cache_->depth_range[0] = 0.0;
  text_depth_cache_->depth_range[1] = 1.0;
}

五行各司其职：

  • MEM_new_zeroed<ViewDepths> — 类型安全的「calloc 一个结构体」。 零初始化很重要：ViewDepths 的 x、y 字段（子矩形偏移） 在这里不使用，靠零值表示「无偏移」；同时避免了手动逐字段初始化的遗漏风险。
  • w / h — 记录数组尺寸，供消费端按下标寻址 depths[y * w + x]，也供 §2.3 的下一帧尺寸比对。
  • GPU_texture_read(...)（分配版重载）— 执行真正的 GPU→CPU 回读， 返回 w × h 个 float 的堆数组。这是整条链路中唯一昂贵的一步。
  • depth_range[2] — 声明本数组的深度值域为 NDC 标准区间 [0, 1]。消费端的比较逻辑以此为尺度依据。

2.6 移交借用指针 1052

overlay_instance.cc : 1052 · 唯一的交接点
DRW_text_cache_depth_set(state.dt, text_depth_cache_);

把 ViewDepths 指针交给文本仓库。头文件注释明确了契约：

draw_manager_text.hh : 41 – 46 · 借用契约
/**
 * Provide the scene depth read-back used by strings flagged with
 * #DRW_TEXT_CACHE_OCCLUSION_CULLING. The store does not take ownership; the caller keeps the
 * #ViewDepths alive until the next #DRW_text_cache_draw. Pass null to disable the tests.
 */
void DRW_text_cache_depth_set(DRWTextStore *dt, const ViewDepths *depths);

关键词是 "does not take ownership"——仓库只存指针（dt->depths = depths;）， 生命期仍由 Instance::text_depth_cache_ 持有。 这就是为什么每个早退分支都要先 depth_set(dt, nullptr) 再 free： 顺序反了，消费端就会在本帧稍后的 DRW_text_cache_draw 里解引用已释放内存。

3.1 ViewDepths 结构体 ED_view3d.hh:91

ED_view3d.hh : 91 – 97
struct ViewDepths {
  unsigned short w, h;
  /* only for temp use for sub-rectangles, added to `region->winx/winy`. */
  short x, y;
  float *depths;
  double depth_range[2];
};
字段类型本函数中的用法
w, hunsigned short记录纹理宽高；消费端按 depths[y * w + x] 寻址；下一帧尺寸比对
x, yshort子矩形偏移，仅特定工具临时使用；此处靠零初始化保持 0
depthsfloat *CPU 侧深度数组，行主序、每像素一个 float NDC 深度
depth_rangedouble[2]值域声明，置为 [0, 1]

注意 w/h 是 unsigned short（最大 65535）。 这不是限制——视口单边超过 64k 像素本就不现实——但消费端寻址 y * w + x 时应使用更宽的整型避免中间溢出（实际消费端用的就是 int）。

3.3 视口与深度纹理获取 wm_draw.cc:954 · gpu_viewport.cc:605

深度纹理在视口初始化时创建（gpu_viewport.cc:174–186）， 有两个对本册重要的细节：

gpu_viewport.cc : 174 – 186 · 深度纹理的创建
if (viewport->depth_tx == nullptr) {
  /* Depth texture can be read back by gizmos #view3d_depths_create. */
  viewport->depth_tx = GPU_texture_create_2d("dtxl_depth",
                                             UNPACK2(size),
                                             1,
                                             gpu::TextureFormat::SFLOAT_32_DEPTH_UINT_8,
                                             usage | GPU_TEXTURE_USAGE_HOST_READ |
                                                 GPU_TEXTURE_USAGE_FORMAT_VIEW,
                                             nullptr);
  const float depth_clear = 0.0f;
  GPU_texture_clear(viewport->depth_tx, GPU_DATA_FLOAT, &depth_clear);
}
  • 格式 SFLOAT_32_DEPTH_UINT_8 — 32 位浮点深度 + 8 位模板（D32S8）。 GPU 侧每纹素 5 字节，但用 GPU_DATA_FLOAT 回读时只取深度面，每像素 4 字节。
  • GPU_TEXTURE_USAGE_HOST_READ — 声明「这张纹理允许 CPU 回读」。 后端据此选择可回读的内存布局。没有这个标志的纹理调用 GPU_texture_read 会触发断言失败（见 §3.4）。视口的深度纹理因为 gizmo、深度探测等多个 子系统都要回读，所以创建时就带上了这个标志。

重载签名内存行为本函数的使用

gpu_texture.cc : 554 – 562 · 写入版与 HOST_READ 断言
void GPU_texture_read(Texture *texture, eGPUDataFormat data_format, int mip_level, void *dst)
{
  BLI_assert(texture);
  BLI_assert_msg(
      GPU_texture_usage(texture) & GPU_TEXTURE_USAGE_HOST_READ,
      "The host-read usage flag must be specified up-front. ...");
  texture->read(mip_level, data_format, dst);   /* GPU 管线同步点 */
}
!

回读是同步操作

texture->read() 需要 CPU 等待 GPU 上所有写入该纹理的工作完成 （隐式管线 flush / fence），是典型的 GPU 停顿源。 这正是「先探测再回读」（§4.1）值得做的原因： 大多数帧（没有属性文本、没有开启遮挡剔除）完全不需要付出这个代价。

3.5 内存分配与释放契约 MEM_guardedalloc.h:550 · view3d_draw.cc:2551

intern/guardedalloc/MEM_guardedalloc.h : 550 – 559 · 类型安全 calloc
template<typename T> inline T *MEM_new_zeroed(const char *allocation_name)
{
  static_assert(std::is_trivial_v<T>, "For non-trivial types, MEM_new must be used.");
  return static_cast<T *>(
      MEM_new_array_zeroed_aligned(1, sizeof(T), alignof(T), allocation_name));
}
  • 只能用于 trivial 类型 —— static_assert 强制约束。 ViewDepths 全是 POD 字段，满足条件。带构造/析构的类型必须用 MEM_new<T>。
  • 零初始化 —— 等价 calloc(1, sizeof(T))， 保证 x/y/depths 从确定值出发。
  • 分配名 —— "ViewDepths" 会出现在内存分析工具中，便于追查泄漏。

释放端同样是一个封装：

{

✓

配对关系一览

MEM_new_zeroed<ViewDepths> 创建的结构体由 ED_view3d_depths_free 整体回收； 其中的 depths 数组由分配版 GPU_texture_read 创建（内部 MEM_new_uninitialized）， 与 MEM_delete 配对。本函数的三处 free + nullptr 调用全部遵循这一配对。

04关键设计决策

4.1 惰性回读：为什么先探测 1019

GPU_texture_read 的成本由两部分构成： 传输（1080p 约 8 MB，见 §8）和同步停顿 （CPU 等待 GPU 排空管线）。前者与分辨率线性相关，后者在驱动层可能触发隐式刷新， 代价远大于传输本身。因此设计成三道闸门，全部通过才回读：

show_text→is_space_v3d→needs_depth_test→回读
全局开关防御检查逐条扫描缓存唯一昂贵步骤

第三道闸门是精确的：needs_depth_test 逐条扫描本帧文本缓存， 只有存在 DRW_TEXT_CACHE_OCCLUSION_CULLING 标志才返回真。 这意味着回读开销只由真正需要遮挡剔除的帧承担—— 比如只有当用户在几何节点编辑器里 pick 了一个 viewer 属性、 且文本标志被置位时，这条路径才会激活。

4.2 跨帧缓存复用 1033–1051

三态逻辑 「尺寸变了 → 重建」「没有 → 新建」「有 → 原地刷新」 保证：

  • 每帧最多一次回读 —— 无论走哪个分支，GPU_texture_read 每帧至多调用一次。
  • 每帧最多一次分配 —— 只有首帧或窗口尺寸变化才 malloc， 常规帧零分配、零释放（原地刷新复用同一块 w×h×4 字节）。
  • 指针稳定性 —— 原地刷新不改变 text_depth_cache_->depths 的值， 即使 dt->depths 里已经借出去的指针依然有效（虽然本函数每帧都会重新 set 一次， 双保险）。
i

为什么不干脆每帧 new + free？

那样每帧多一对 malloc/free（约 8 MB 的大块分配，可能触发向操作系统申请新页）， 且新旧指针地址不同，任何持有旧指针的路径（哪怕只是断言期间的）都有悬垂风险。 复用 + 原地刷新在性能与安全两方面都更优。

4.3 所有权模型：拥有 vs 借用 1052

角色指针权责
拥有者 Instance::text_depth_cache_ 负责 MEM_new_zeroed 创建与 ED_view3d_depths_free 释放；生命期覆盖整帧
借用者 DRWTextStore::depths 只读使用；不释放；依赖拥有者在释放前先 depth_set(nullptr) 摘除指针

这个设计是 Blender 大量使用的「borrowed pointer」模式： 数据生产方（覆盖层引擎）与消费方（文本绘制）解耦， 文本仓库不需要知道 ViewDepths 怎么来的、何时失效。 代价是时序契约：借用窗口必须覆盖消费端的使用窗口 （update_text_depth() → draw_text() → DRW_text_cache_draw()）， 本函数把 set 放在最后一行、把摘除放在每个早退分支的第一行，正是为了维护这个窗口。

4.4 const_cast 为什么安全 1029

为什么需要 const_cast
GPUViewport *viewport = WM_draw_region_get_viewport(const_cast<ARegion *>(state.region));
/* state.region 是 const ARegion *，而 API 签名是 ARegion *（非 const） */

WM_draw_region_get_viewport 是旧式 C 风格 API，签名没有 const 化， 但其实现（见 §2.2）只读取 region->runtime->draw_buffer->viewport， 不写入任何字段。覆盖层引擎的 state.region 是 const 的， 于是这里用 const_cast 桥接。安全性依据： 被转换的对象本身不是 const 定义的（上游以非 const 持有），去掉 const 不会触发未定义行为； 真正的保障是「实现只读」这一事实，而不是类型系统。

08尺寸与开销验算

用 1920×1080 视口走一遍数字，感受各环节的实际量级：

成本核算 · 1920 × 1080 视口
像素数        = 1920 × 1080                      = 2,073,600 px
GPU 侧纹理    = 2,073,600 × 5 B (D32S8)          ≈ 9.88 MiB   ← 显存常驻，与本函数无关
CPU 回读数组  = 2,073,600 × 4 B (float)          ≈ 7.91 MiB   ← 分配版唯一一次分配
原地刷新      = 每帧覆盖写 7.91 MiB，零分配                    ← §2.5 路径
needs_depth_test 扫描 = O(缓存文本条数)，通常 < 几百条，纳秒级  ← §2.1 探测
回读同步      = 一次隐式管线 flush，量级取决于驱动与在途工作     ← 真正的代价
i

数字背后的设计结论

扫描缓存（纳秒级）与回读（毫秒级，含同步）相差五个数量级以上—— 所以「先花纳秒探测、再决定是否花毫秒回读」的惰性策略几乎总是划算的。 而 7.91 MiB 的缓冲若每帧重新分配，不仅多两次大块 malloc/free， 还会把「跨帧指针稳定性」这一隐含福利丢掉——这就是三态缓存逻辑存在的意义。
