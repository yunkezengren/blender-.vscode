00一句话回答

perspmat 不是 GL 状态机里那个单独的 GL_PROJECTION 矩阵，而是

persmat = winmat · viewmat = P · V

也就是图形学里常说的 VP 矩阵（View-Projection）：一次矩阵乘法直接把世界空间坐标送到裁剪空间。

所谓"已合成"，是指本该在 GPU 顶点着色器里分两步完成的

顶点着色器 · 等价的传统写法
vec4 clip = P * (V * vec4(pos, 1.0));

被提前乘成一步 (P·V) * vec4(pos, 1.0)，并把结果缓存在 rv3d->persmat 里。

i

代价与收益

代价：每次视口重绘算一次 4×4 矩阵乘法（view3d_draw.cc:135）。

收益：每次投影少一次 4×4 矩阵乘法 —— 而投影处在极热的循环里（选中拾取、边迭代器、gizmo 绘制，每帧对每个顶点调用）。

02为什么"合成"在数学上完全免费

2.1 结合律

矩阵乘法满足结合律：

(P · V) · v  =  P · (V · v)

先把 viewmat 和 winmat 乘起来存好，跟每次投影时连乘两次，结果逐位相同（浮点误差量级也基本一致）。差别只在计算次数：前者是每次重绘 1 次矩阵乘法，后者是每次投影 2 次矩阵-向量乘法。所以预合成是纯粹的性能优化，不改变任何语义。

2.2 Blender 的存储约定：m[列][行]，列主序

float mat[4][4] 在内存里是 16 个连续 float，mat[i] 是第 i 列。这样可以直接喂给 glUniformMatrix4fv(..., GL_FALSE, ...) 而不用转置。所以：

mat[c][r] = Mr,c   ，   mat[3][0..2] = 平移分量
!

读 Blender 矩阵代码时，下标顺序和数学教科书是反的

这是第一个高频踩坑点。m[2][3] 指的是第 3 列第 2 行，也就是数学矩阵的第 3 行第 2 列。

2.3 乘法约定：mul_m4_m4m4(R, A, B) 计算 R = A · B

math_matrix_c.cc:226 的注释 R[j][k] = B[j][i] . A[i][k] 用的正是 [列][行] 下标。展开验证第 0 项（math_matrix_c.cc:245）：

math_matrix_c.cc : 245
R[0][0] = B[0][0]*A[0][0] + B[0][1]*A[1][0] + B[0][2]*A[2][0] + B[0][3]*A[3][0];

换成标准数学下标（把 X[c][r] 记作 Xr,c）：

R0,0 = B0,0A0,0 + B1,0A0,1 + B2,0A0,2 + B3,0A0,3 = Σk A0,kBk,0 = (A · B)0,0

所以 mul_m4_m4m4(R, A, B) 得到 R = A · B，语义是"先作用 A，再作用 B"（对列向量左乘而言）。这就对上了：

  • mul_m4_m4m4(persmat, winmat, viewmat) → persmat = P · V → 先 viewmat 后 winmat，即世界 → 视图 → 裁剪，顺序正确。
  • mul_m4_m4m4(persmatob, persmat, object_to_world) → P · V · M，物体空间先经过 M。

2.4 原地乘法的别名安全性

mul_m4_v4(mat, r) 内部是 mul_v4_m4v4(r, mat, r)（math_matrix_c.cc:812），输入输出是同一块内存。看实现（math_matrix_c.cc:798-808）：

math_matrix_c.cc : 798 – 808
void mul_v4_m4v4(float r[4], const float mat[4][4], const float v[4])
{
  const float x = v[0];   /* 先读进局部变量 */
  const float y = v[1];
  const float z = v[2];

  r[0] = x * mat[0][0] + y * mat[1][0] + z * mat[2][0] + mat[3][0] * v[3];
  r[1] = x * mat[0][1] + y * mat[1][1] + z * mat[2][1] + mat[3][1] * v[3];
  r[2] = x * mat[0][2] + y * mat[1][2] + z * mat[2][2] + mat[3][2] * v[3];
  r[3] = x * mat[0][3] + y * mat[1][3] + z * mat[2][3] + mat[3][3] * v[3];
}

先把 v[0..2] 读进局部变量，写 r[0..2] 时不再依赖原值，最后才读 v[3] —— 所以别名是安全的。第 122 行正依赖这一点。

03齐次坐标与射影几何

这是理解 120–135 行全部数学的地基。

3.1 仿射点的齐次嵌入

三维仿射空间 𝔸³ 中的点 (x, y, z) 嵌入射影空间 ℙ³ 时写成 (x, y, z, 1)。这就是 120–121 行在干的事：

view3d_project.cc : 120 – 121
copy_v3_v3(vec4, co);
vec4[3] = 1.0;

补上那个 1，是为了让 4×4 矩阵能同时表达线性变换和平移 —— 纯线性变换只能表达过原点的变换；平移在 𝔸³ 里是仿射而非线性映射，但在 ℙ³ 里它就是一个货真价实的线性映射。

3.2 射影等价与透视除法

ℙ³ 的元素是等价类：任何非零 λ 缩放的四个数代表同一个射影点

(x, y, z, w)  ∼  (λx, λy, λz, λw)   ，   λ ≠ 0

为了回到唯一的仿射坐标，约定"归一化到 w = 1"，于是必须除以 w：

(xc, yc, zc, w)  ⟼  (xcw, ycw, zcw, 1)

这就是"透视除法"（perspective divide）的全部来历 —— 它不是图形学发明的技巧，而是射影几何的定义直接推出来的。第 138–139 行的 * scalar（= 1/w）干的就是这件事。

3.3 w = 0 是无穷远点

w = 0 的射影点是无穷远点：无论 λ 怎么缩放，都无法把 w 变成 1，因此无法映射回仿射空间。这解释了：

  • 第 125 行 CLIP_ZERO 的存在 —— 必须显式拦截这类点；
  • 第 137 行那个兜底 (w != 0.0f) ? (1.0f / w) : 0.0f —— 防止产生 inf / NaN 污染后续计算。

04针孔相机模型：为什么 w = −zview

4.1 相似三角形

真实相机成像的基本关系是相似三角形：物体离得越远，成像越小，缩放因子恰为 1/深度。

xndc ∝ xview−zview   ,   yndc ∝ yview−zview

负号是因为 Blender / OpenGL 约定相机朝 −z 方向看，所以相机前方的点满足 zview < 0，于是 −zview > 0 才是正的深度。

要让后续的"除以 w"自动实现这个 1/深度，就必须让 w 正比于深度。

4.2 frustum 矩阵展开

看 gpu/intern/gpu_matrix.cc:309-333 的 mat4_frustum_set：

gpu_matrix.cc : 312 – 330
m[0][0] = 2.0f * near / (right - left);
m[1][1] = 2.0f * near / (top - bottom);
m[2][2] = -(far + near) / (far - near);
m[3][2] = -2.0f * far * near / (far - near);
m[2][3] = -1.0f;   /* 存储下标 [列][行] = 数学上的第 3 行第 2 列 */

展开成标准数学矩阵（记 n = 近裁剪面，f = 远裁剪面，l, r, b, t 为视锥四边界）：

P =
2nr−l 0 r+lr−l 0
0 2nt−b t+bt−b 0
0 0 −f+nf−n −2fnf−n
0 0 −1 0

用 mul_v4_m4v4 的公式算第 4 个分量：

w = x·0 + y·0 + z·(−1) + 1·0 = −zview

精确成立。 所以"除以 w"就等价于"除以深度"，透视缩放自动实现。

★

第 4 行 (0, 0, −1, 0) 就是整个透视投影的灵魂

它是唯一让 w ≠ 1 的一行。没有它，透视投影就退化成正交投影。

4.3 正交矩阵对比

gpu_matrix.cc:283-304 的 mat4_ortho_set，第 4 行是 (0, 0, 0, 1)，所以：

w ≡ 1

除法变成恒等操作，没有透视缩放 —— 这正是正交投影的定义。

05120–122 行的逐步数值演示

取 n = 0.1、f = 1000，视锥上下左右对称（l = −r、b = −t），于是 (r+l)/(r−l) = 0、(t+b)/(t−b) = 0，矩阵简化为对角形式。

取世界空间中相机正前方 10 个单位处、且 xview = yview = 0 的点，则 zview = −10：

手算推演 · n = 0.1, f = 1000
第 1 步  copy_v3_v3(vec4, co);      →  vec4 = [0, 0, -10, ?]
第 2 步  vec4[3] = 1.0;             →  vec4 = [0, 0, -10, 1]     ← 齐次嵌入
第 3 步  mul_m4_v4(perspmat, vec4);

         x_c = 2n/(r-l) · 0                         = 0
         y_c = 2n/(t-b) · 0                         = 0
         z_c = -(f+n)/(f-n) · (-10) + (-2fn/(f-n)) · 1
             = (1000.1/999.9) · 10 − 200/999.9
             = 10.0010 − 0.2000                     = 9.8010
         w   = -1 · (-10)                           = 10      ← w = -z_view

得到裁剪空间坐标 (0, 0, 9.801, 10)，且 zc/w = 0.9801，落在 [−1, 1] 内，可见。

06第 123 行：fabsf 到底改了什么

view3d_project.cc : 123
const float w = fabsf(vec4[3]);

w 从此不再是"齐次坐标的第 4 分量"，而变成了"该点到相机平面的距离"（以视图空间单位为量纲）。 三个后果：

  1. 第 137 行 scalar = 1/w 恒为正，所以 xc/|w| 与真正的射影值 xc/vec4[3] 相差一个符号 —— 相机背后的点会被投影到镜像位置，而不是被拒绝。
  2. CLIP_ZERO 的语义被改写：从"w 为负或为零"变成"到相机平面的距离 ≤ 0.001"。否则所有相机背后的点都会被误报成 CLIP_ZERO。
  3. 真正负责拦截背后点的是 CLIP_NEAR（第 129 行），推导见下一节。

对比文件开头 32–51 行的"不裁剪版"：

view3d_project.cc : 43 – 49 · 不裁剪版，用原始 vec4[3]
if (vec4[3] > FLT_EPSILON) {          /* 只对前方点做除法 */
  co_region[0] = region->winx / 2.0f + (region->winx / 2.0f) * vec4[0] / vec4[3];
  co_region[1] = region->winy / 2.0f + (region->winy / 2.0f) * vec4[1] / vec4[3];
}
else {
  zero_v2(co_region);                 /* 背后点 → (0,0)，没有状态码 */
}

它用的是原始 vec4[3]（保留符号），代价是无法区分"背后"和"恰好在相机平面上"，也没有任何状态码返回。裁剪版（本段）改用 |w| 加独立的状态码，把"背后"这件事显式交给 CLIP_NEAR 处理 —— 这是一次职责的重新划分，不是随手取了个绝对值。

07125–135 行：不做除法的"交叉相乘"比较

这三行是整段代码最精巧的地方。它们的数学本质是把有理不等式 zc/w ≶ ±1 两边同乘 w，变成有界浮点乘法。

7.1 CLIP_NEAR 推导（第 129 行）

view3d_project.cc : 129 – 131
if ((flag & V3D_PROJ_TEST_CLIP_NEAR) && (vec4[2] <= -w)) {
  return V3D_PROJ_RET_CLIP_NEAR;
}

GL 的裁剪空间约定是 zc/w ∈ [−1, 1]，其中 −1 对应近平面。两边同乘 w > 0：

zcw ≤ −1   ⟺   zc ≤ −w

7.2 近/远平面映射验算

近平面 zview = −n：

zc = −f+nf−n·(−n) − 2fnf−n = n(f+n) − 2fnf−n = n² − nff−n = −n

而 w = −zview = n，所以 zc/w = −n/n = −1 ✓

远平面 zview = −f：

zc = −f+nf−n·(−f) − 2fnf−n = f(f+n) − 2fnf−n = f² − fnf−n = f

而 w = f，所以 zc/w = f/f = +1 ✓

7.3 CLIP_FAR 推导（第 133 行）

view3d_project.cc : 133 – 135
if ((flag & V3D_PROJ_TEST_CLIP_FAR) && (vec4[2] >= w)) {
  return V3D_PROJ_RET_CLIP_FAR;
}

同一套推导，zc/w ≥ +1 ⟺ zc ≥ w。

7.4 为什么必须"先判后除"

  1. 省一次除法：浮点除法延迟通常是乘法的 4–20 倍，在每帧数万次的顶点循环里很可观。
  2. 数值稳健：w 极小时 zc/w 会溢出成 inf，或产生灾难性抵消（catastrophic cancellation）；而 zc 与 w 的比较始终是良态的有界比较。除法被推迟到所有可能出问题的点都已经被过滤之后 —— 这正是第 137 行排在 125–135 行之后的原因。
  3. 数学等价：两个不等式合起来恰好是 |zc| > w 的两个半边，与 |zc/w| > 1 完全等价。

因为 zc 随 zview 增大而急剧变负，必然跌破 −w。这也正是 ED_view3d.hh:313-316 要求"透视视图必须把 CLIP_WIN 和 CLIP_NEAR 一起打开"的原因。

7.6 深度精度分布

把 zview = −d（d > 0 为深度）代入，得到 NDC 深度关于深度的解析式：

ndc(d) = zcw = (f+n)·d − 2fn(f−n)·d   → (n=0.1, f=1000)   1000.1·d − 200999.9·d
深度 d 0.10.150.20.30.5 1251020
ndc −1.000−0.3330.0000.3340.600 0.8000.9000.9600.9800.990

这张表揭示了一个经典现象：深度精度严重非均匀。

  • d ∈ [0.1, 1] 这一小段就用掉了 NDC 的 40%（−1 → 0.80）
  • d ∈ [1, 10] 用掉约 18%
  • d ∈ [10, 1000] 全部挤在最后 2% 里

d → 0⁺ 时曲线冲向 −∞，这就是 CLIP_ZERO 存在的理由。这也是所有透视深度缓冲（z-fighting）问题的数学根源。

08正交投影下的退化

正交矩阵 w ≡ 1，于是：

  • CLIP_NEAR：zc ≤ −1；CLIP_FAR：zc ≥ 1 —— 判据依旧精确（7.2 节已验算近远平面分别映射到 ∓1）。
  • CLIP_ZERO 永远不会触发（1 > 0.001）：没有除法，也就不存在 w → 0 的奇点。
  • "相机背后"在正交下不再是奇点：正交投影是仿射映射，zview > 0 的点只会因为落在 [−n, −f] 这个立方体视景体之外而被 NEAR 裁掉 —— 这与透视下"投影奇点"是完全不同的物理原因。

09一个容易踩的坑：CLIP_CONTENT 不在这里

V3D_PROJ_TEST_ALL 包含 V3D_PROJ_TEST_CLIP_CONTENT（所以第 109 行的断言能通过），但 120–135 行从不检查这一位。

它由 view3d_iterators.cc 的边迭代器消费，语义是"把跨越视口边界的边裁剪到边界上"（见 ED_view3d.hh:301-321），与单点投影无关。
