01宏观：谁在调用它 —— DrawEngine 继承体系

这个函数是成员函数，宿主类是 blender::draw::overlay::Instance。 它不是孤立的类，而是插件式渲染引擎架构中的一个节点。 整段代码里唯一真正的面向对象在引擎层—— 数据层（State、ViewDepths、GPUViewport、wmDrawBuffer） 全部是无虚函数的 POD 结构体。

1.1 虚函数与工厂 DRW_render.hh:71–133

DRW_render.hh : 71 – 97 · 抽象基类

  virtual void init() = 0;                  /* 每帧最先跑 */

  virtual void end_sync() = 0;

七个纯虚函数构成引擎生命周期模板。Pointer 嵌套结构（104–132 行）是工厂： 持有基类指针 DrawEngine *instance，set_used(true) 时若为空就调 第二个纯虚函数 create_instance() 创建具体引擎—— draw_view_data.cc 的 foreach_engine 遍历所有注册引擎完成这个分发。

✓

虚析构是整个资源契约的基石

Pointer::free_instance() 执行 delete instance——基类指针删除派生类对象。 正因为 DrawEngine 声明了虚析构（78 行），这次 delete 才能正确调到 overlay::Instance::~Instance()（overlay_instance.hh:120–126）， 后者释放 text_depth_cache_——本函数管理的内存的最终兜底。

03三条件早退逐行 1019–1026

overlay_instance.cc : 1019 – 1026
if (!state.show_text || !state.is_space_v3d() || !DRW_text_cache_needs_depth_test(state.dt)) {
  DRW_text_cache_depth_set(state.dt, nullptr);   /* ① 先摘借用指针 */

  • || 短路求值：两个 bool 最便宜放前面，O(n) 缓存扫描放最后——前两关不过就不付扫描成本。
  • 探测函数（draw_manager_text.cc:342–350）：遍历 cache_strings， 任一条 flag & DRW_TEXT_CACHE_OCCLUSION_CULLING（1 << 4）即真。 这个标志只被 overlay_attribute_text.hh 的 text_flag_ 打上—— 只有 .viewer 属性文本申请遮挡剔除，普通物体名标签不申请。
  • 早退顺序是安全契约：先置空 dt->depths 再 free。 反序且本帧仍有带标志文本时，消费端 dt->depths->depths[...] 就是 use-after-free。

04ViewDepths 与姊妹实现

ED_view3d.hh : 91 – 97 · 普通 struct，零虚函数
struct ViewDepths {
  unsigned short w, h;        /* 数组尺寸 */
  short x, y;                 /* 子矩形偏移，本场景恒 0 */
  float *depths;              /* CPU 深度数组，行主序 */
  double depth_range[2];      /* 值域声明 [0,1] */
};

它不是为本功能发明的。同一个结构体早已服务 gizmo 深度拾取—— view3d_draw.cc:2405 有几乎一模一样的 view3d_depths_create()： 同样的 MEM_new_zeroed<ViewDepths>、同样的取纹理、同样的 GPU_texture_read(depth_tx, GPU_DATA_FLOAT, 0)。 本函数是它的跨帧复用改造版：增加尺寸检测与原地刷新，其余一致。

MEM_new_zeroed<T>（MEM_guardedalloc.h:550–559）能用于 ViewDepths 是因为它全 POD；模板内的 static_assert(std::is_trivial_v<T>) 会拒绝任何带 构造/析构的类型。释放端 ED_view3d_depths_free（view3d_draw.cc:2551–2557）两步走： 先 MEM_delete(depths->depths) 再 MEM_delete(depths)，与本函数的分配严格配对。

5.2 深度纹理的诞生 gpu_viewport.cc:174–186

viewport->depth_tx = GPU_texture_create_2d("dtxl_depth",

  • SFLOAT_32_DEPTH_UINT_8 = D32S8：32 位浮点深度 + 8 位模板。 浮点深度是 Blender 近平面极高精度的关键（第 1 册 §6）。
  • GPU_TEXTURE_USAGE_HOST_READ（GPU_texture.hh:770，第 4 位）： 显式声明「CPU 要回读」。Vulkan/Metal 的 usage 必须创建时声明，后端据此选择可回读内存布局。 缺了这个标志调 GPU_texture_read 直接断言失败（gpu_texture.cc:557–560）。
  • FORMAT_VIEW：允许格式视图——Workbench 体积渲染要读 stencil 视面。

06gpu::Texture 多态分发 —— 本函数触发的唯一真 OO

GPU_texture_read 最深处藏着整段代码唯一的运行期多态：

gpu_texture_private.hh : 105 – 175 · 抽象基类（protected 字段 + 纯虚）
class Texture {
 protected:
  int w_, h_, d_;                        /* 尺寸 */
  TextureFormat format_;                 /* 内部格式 */
  eGPUTextureUsage gpu_image_usage_flags_;  /* HOST_READ 存这里 */
  Texture *source_texture_ = nullptr;    /* 纹理视图源 */
 public:
  virtual ~Texture();                    /* 虚析构 */
  virtual void read(int mip, eGPUDataFormat format, void *dst) = 0;  /* ← 纯虚 */
  int width_get() const { return w_; }   /* 非虚内联 */
};

6.1 GL 后端 read() gl_texture.cc:483–526

Windows 上 Blender 默认走这条
void GLTexture::read(int mip, eGPUDataFormat type, void *data)
{
  /* 深度+模板纹理读回时剥离 stencil */
  GLenum gl_format = to_gl_data_format(
      format_ == TextureFormat::SFLOAT_32_DEPTH_UINT_8
          ? TextureFormat::SFLOAT_32_DEPTH : format_);
  const int3 extent = mip_size_get(mip);
  if (is_texture_view() && format_get() == source_texture_->format_get()) {
    glGetTextureSubImage(static_cast<GLTexture *>(source_texture_)->tex_id_, ...);
  } else {
    glGetTextureSubImage(tex_id_, mip, 0,0,0, extent.x, extent.y, extent.z,
                         gl_format, gl_type, texture_size, data);
  }
}

glGetTextureSubImage 是隐式同步点：CPU 阻塞直到 GPU 完成所有影响该纹理的命令 （管线排空 / fence）。这就是「回读是管线停顿源」的底层机制。 纹理视图分支规避了 OpenGL 驱动对视图尺寸处理不佳的问题。

6.2 Vulkan 后端 read() vk_texture.cc:336–361 → read_sub:204

Vulkan 没有直接「读纹理」，要四步： 分配 staging 传输缓冲 → vkCmdCopyImageToBuffer → 带内存屏障等传输完成 → CPU 侧格式转换。 read_sub 还处理超大纹理分块（#144887：NVIDIA 传输缓冲上限 2GB）， 超过就按层 / 按深度 / 按行拆分多个 transfer region 逐段搬。

6.3 双重载与 HOST_READ gpu_texture.cc:538–562

分配版（1043 行用）与写入版（1050 行用）
void *GPU_texture_read(Texture *texture, eGPUDataFormat fmt, int mip)
{
  size_t size = texture->read_size_get(mip, fmt);   /* w*h*4 字节 */
  if (texture->type_get() == GPU_TEXTURE_CUBE_ARRAY) size += 8;  /* AMD bug #66573 */
  void *data = MEM_new_uninitialized(size, __func__);
  GPU_texture_read(texture, fmt, mip, data);        /* 转调写入版 */
  return data;
}

void GPU_texture_read(Texture *texture, eGPUDataFormat fmt, int mip, void *dst)
{
  BLI_assert_msg(GPU_texture_usage(texture) & GPU_TEXTURE_USAGE_HOST_READ, "...");
  texture->read(mip, fmt, dst);                     /* ← 虚函数分发 */
}

两个重载的真正差别只在内存归谁管。本函数的妙处： 首帧用分配版让 depths 拿到堆内存，之后每帧用写入版原地覆盖—— depths 指针值永不改变。数据布局结论： w×h 个 IEEE-754 float，行主序，每个是 NDC 深度 ∈ [0,1]。

1052 行交出指针后，同帧稍后 draw_text()（1009 行）→ DRW_text_cache_draw()（draw_manager_text.cc:244）。三步消费：

投影取深度 → 采样 → 比较（draw_manager_text.cc:260 · 284 · 187–191）
/* ① 投影时顺带取锚点深度（第 2 册的函数，最后出参） */
ED_view3d_project_float_ex(region, rv3d->persmat, ..., &anchor_depth)

/* ② 采样场景深度：行主序寻址 */
const float scene_depth = dt->depths->depths[y * dt->depths->w + x];

/* ③ bias 比较，bias = 2.0e-5f */

{
  return scene_depth != 1.0f && anchor_depth > scene_depth + text_depth_bias;

08GPU / CPU 基础知识

概念在本函数中的体现
深度缓冲 Depth Buffer每像素一个深度值的离屏纹理；prepass 由场景几何写入；depth_tx 就是它
NDC 深度 [0,1]透视除法后的深度；0 = 近平面，1 = 远平面；回读数组里存的就是它
D32S8 复合格式32 位浮点深度 + 8 位模板打包 5 字节/纹素；读回只取深度面 → 4 字节/像素
CPU–GPU 异步CPU 提交命令、GPU 异步执行，平时互不等待 → 吞吐高
回读同步代价glGetTextureSubImage / vkCmdCopyImageToBuffer 必须等 GPU 排空 → 管线停顿，惰性回读的动机
Usage 标志Vulkan/Metal 要求创建时声明用途；HOST_READ 启用 CPU 可读内存布局，并禁用某些压缩
行主序 Row-majordepths[y * w + x] 的寻址公式；一行连续，行间跳 w 个 float
POD / Trivial只有平凡类型能用 MEM_new_zeroed；ViewDepths / State / GPUViewport 全满足
