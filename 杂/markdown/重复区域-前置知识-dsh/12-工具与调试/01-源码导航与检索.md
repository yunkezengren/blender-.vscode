> 基准：Blender `5.4.0-alpha`，本地工作树。本篇讲方法论：在一个约 300 万行、数万文件的仓库里，如何快速定位"某条语义在哪里实现"。它不讲任何具体机制，只讲怎么找。

## 先回答一个具体问题

你读正篇时看到一个陌生符号，比如 `RepeatZoneSideEffectProvider`。下一步该做什么？

错误做法：从 `source/blender/` 开始翻目录。正确做法：**grep 符号名 → 定位定义 → 读文件头注释 → 反查调用方 → 交叉验证**。

这套流程本篇会拆成五步，每步给出具体命令与判据。

## Blender 源码的目录结构

`[讲解]` 先建立地图感。Blender 的核心目录不是按"功能"分的，而是按"层"分的：

| 目录 | 职责 | 规模感 |
| --- | --- | --- |
| `source/blender/blenlib/` | 基础库（BLI）：容器、数学、内存、字符串 | 250 个 `BLI_*.hh` |
| `source/blender/blenkernel/` | 核心数据与业务逻辑（BKE）：Mesh、GeometrySet、节点树、依赖图 | 数百个 `BKE_*.hh` |
| `source/blender/makesdna/` | 可序列化的 C 结构定义（DNA） | 97 个 `DNA_*.h` |
| `source/blender/makesrna/` | 运行时反射层（RNA） | `RNA_*.hh` + `intern/rna_*.cc` |
| `source/blender/functions/` | 函数式求值框架（FN）：MultiFunction、Field、LazyFunction | 21 个 `FN_*.hh` |
| `source/blender/nodes/` | 节点系统：注册、声明、几何节点实现 | 上千文件 |
| `source/blender/compositor/` | 合成器后端 | `COM_*.hh` |
| `source/blender/gpu/` | GPU 后端与着色器 | 含 `.bsl.hh` 等着色器模板 |
| `source/blender/editors/` | 编辑器 UI 与操作符 | 按 space 分（`space_node/` 等） |
| `source/blender/blenloader/` | .blend 读写与版本迁移 | `versioning_*.cc` |

`[讲解]` 命名前缀就是层标识：`BLI_` = 基础库，`BKE_` = 核心，`DNA_` = 存储，`RNA_` = 反射，`FN_` = 函数框架，`NOD_` = 节点系统通用，`COM_` = 合成器，`GPU_` = GPU。

**记住前缀，就能从文件名猜出层次**——这是 Blender 代码库少见的自律。

## 五步定位法

### 第一步：grep 符号名

```bash
grep -rn "RepeatZoneSideEffectProvider" source/blender/
```

`[讲解]` 三个技巧：

1. **用 `-r` 递归、`-n` 显示行号**。不要忘记 `-n`，否则找到也不知道在哪行。
2. **限定目录**。全仓库搜会很慢，先猜大方向（节点系统 → `source/blender/nodes/`）。
3. **注意大小写**。Blender 命名用 PascalCase（类型）与 snake_case（函数），精确匹配更快。

如果符号太常见（比如 `Map`），加上下文词：

```bash
grep -rn "class Map" source/blender/blenlib/
```

### 第二步：定位定义

`[讲解]` 找到多个结果后，按这个优先级读：

| 结果形态 | 判据 | 优先级 |
| --- | --- | --- |
| `class Foo {` / `struct Foo {` | 定义 | ★★★ 先读这个 |
| `Foo::Foo(` | 构造函数 | ★★ |
| `Foo::method(` | 方法实现 | ★★ |
| `Foo(...)` | 调用点 | ★ 最后读 |
| 注释里提到 | 参考 | 忽略 |

**为什么先读定义？** 因为定义带注释、带字段、带方法签名——一次就能建立整体印象。调用点只在需要理解"怎么用"时才读。

### 第三步：读文件头注释

`[讲解]` Blender 的头文件几乎都有 `/** \file ... */` 块，这是**最高密度的信息源**。

例子（本篇不用真源码，给结构性示例）：

```cpp
/** \file
 * \ingroup bli
 *
 * An `Span<T>` references an array that is owned by someone else. ...
 */
```

`[讲解]` 三个判据：

1. **`\ingroup`** 告诉你它属于哪个模块；
2. **第一段话**通常是"这个类型解决什么问题"——比任何博客都准；
3. **"NOTE"、"WARNING"、"Known issues"** 段落往往记录了设计取舍，是最有价值的部分。

**实操建议**：找到定义后，先读定义**之前**的 30-80 行注释，再读定义本身。

### 第四步：反查调用方

```bash
grep -rn "RepeatZoneSideEffectProvider" source/blender/ | grep -v "^.*\.hh:"
```

`[讲解]` 用 `grep -v` 过滤掉头文件，只看实现文件——因为调用方通常在 `.cc`。

**读调用方的三个问题**：

1. 谁构造它？（构造点揭示生命周期）
2. 谁传给谁？（参数流向揭示依赖）
3. 有没有传 `nullptr`？（可选性揭示设计意图）

### 第五步：交叉验证

`[讲解]` 单点证据不可靠。至少找两类独立证据：

| 证据类型 | 例 |
| --- | --- |
| 定义处注释 | 说"这是可选的" |
| 调用处实参 | 有时传 nullptr，有时传实例 |
| 断言 | `BLI_assert(ptr != nullptr)` 说明实际不允许空 |

三者一致才算确认。**如果注释与代码矛盾，以代码为准，并在笔记里记下这个矛盾**——这类矛盾往往是理解历史演化的入口。

## 快速判据表

`[讲解]` 一张表把"看到什么 → 说明什么"固化下来：

| 看到 | 说明 |
| --- | --- |
| `virtual ... = 0;` | 纯虚，必须由子类实现 |
| `virtual ... override` | 子类覆盖 |
| `BLI_assert(...)` | Debug 构建的前置条件（Release 会消失） |
| `static_cast<T*>(void_ptr)` | 类型擦除后的还原，要找谁设置的 |
| `const_cast<T&>` | 接口保守但实现需要修改，通常是框架边界 |
| `std::optional<T>` | "可能没有"，语义比空指针清晰 |
| `[[maybe_unused]]` | 参数/变量确实不用，通常是接口对齐 |
| `// TODO:` / `/* TODO */` | 已知未完成，读它往往能理解设计边界 |
| `#ifdef __cplusplus` | DNA 头里的 C++ 扩展，C 侧看不到 |

## 三个实用技巧

### 技巧 1：无 shell 环境下的行数探测

`[讲解]` 本系列早期有一段时间 PowerShell 因沙箱故障不可用，改用 `read` 工具探测：

```
read(file_path, offset=99999, limit=2)
→ Error: offset 99999 is out of range for "..." (N lines)
```

返回的 `N` 就是总行数。对任何只能读文件的环境都适用。

### 技巧 2：用 git log -L 追踪函数演化

```bash
git log -L :initialize_execution_graph:source/blender/nodes/intern/geometry_nodes_repeat_zone.cc
```

`[讲解]` 这条命令列出**该函数的每一次变更**。用途：

- 看某个设计是"一开始就有"还是"后来补的"；
- 看注释里提到的"另一种方案"是否曾实现过；
- 找到引入某个字段的提交，读提交说明理解动机。

### 技巧 3：用 why_file 查本地会话历史

`[讲解]` 本环境提供的 `why_check(path)` / `why_file(path)` 能查"这个文件在本地 agent 会话里被谁改过、为什么改"。

典型用法：

1. `why_check` 先问"有没有历史"（一行）；
2. 有则 `why_file` 列出触及它的轮次（时间、问题、改动、结论）；
3. 需要细节时 `why_recall(session, turn)` 读完整轮次。

这对"理解某个改动为什么这么写"极有效，比读 diff 快。

## 一个完整的检索实例

`[讲解]` 以"Repeat 的 Iterations 为什么永不被裁剪"为例，走完五步：

**第一步 grep 符号**：

```bash
grep -rn "ValueUsage::Used" source/blender/nodes/intern/geometry_nodes_repeat_zone.cc
```

**第二步定位定义/赋值**：找到 `inputs_[zone_info_.indices.inputs.main[0]].usage = lf::ValueUsage::Used;`（约 L136）。

**第三步读注释**：构造函数前面有注释 `/* Iterations input is always used. */` —— 直接给出理由。

**第四步反查**：

```bash
grep -rn "output_was_set" source/blender/nodes/intern/geometry_nodes_repeat_zone.cc
```

发现 `execute_impl` 里还有一处 `if (!params.output_was_set(iterations_usage_index))` 的兜底。

**第五步交叉验证**：

- 定义处注释说"always used"；
- 执行期还有兜底写入；
- 静态推断器对 Repeat Input 是保守规则。

三者一致，结论：**两处配合保证 Iterations 永不被裁剪**。

`[讲解]` 注意这个实例的价值不在结论，而在**流程**：每一步都可以复制到任何"某条语义在哪实现"的问题上。

## 反例与边界

### 反例 1：只搜函数名不搜类型名

`[讲解]` 想找"Repeat 的副作用怎么处理"，只搜 `side_effect` 会命中上百处。应该先搜类型 `RepeatZoneSideEffectProvider`，再顺藤摸瓜。

### 反例 2：跳过文件头注释直接读代码

`[讲解]` Blender 的头注释质量极高，跳过等于扔掉最好的文档。

### 反例 3：相信注释多于代码

`[讲解]` 注释会过时。看到 `/* 这里是 XXX */` 时，用代码验证一下。矛盾处要记录。

### 反例 4：只看 `.hh` 不看 `.cc`

`[讲解]` 头文件是接口，实现细节全在 `.cc`。很多关键决策（比如"这里为什么不缓存"）只写在 `.cc` 的注释里。

### 反例 5：忽略 `_generic.hh` 之类的模板实现文件

`[讲解]` Blender 大量用模板 + 显式实例化，把实现在 `*_generic.hh` 里。搜不到实现时，找找同名 `_generic` 文件。

## 对理解 Repeat 的帮助

`[讲解]` 本系列全部结论都是这套流程的产物。举例：

| 结论 | 检索路径 |
| --- | --- |
| wrapper 优于每轮独立 LazyFunction | grep `GraphExecutorNodeExecuteWrapper` → 读注释 → 找到取舍说明 |
| 图构建不缓存 | grep `initialize_execution_graph` → 读 L187-L194 注释 |
| 0 轮直通 | grep `iterations == 0` → 找到分支 |

掌握了方法，你不需要这份文档也能得出同样结论——这才是本篇的目的。

## 用小数据走一遍

真实演练：回答"Repeat 的 `output_node_id` 到底在哪被赋值"。全程只用检索工具，不凭记忆。

| 步 | 动作 | 命令 | 结果 |
| --- | --- | --- | --- |
| 1 | 定起点：字段名在 DNA 里的定义 | grep `output_node_id` include `DNA_node_types.h` | 命中 `NodeGeometryRepeatInput.output_node_id`（含注释"bNode.identifier of the corresponding output node"） |
| 2 | 全仓写侧搜索：谁给 `.output_node_id =` 赋值 | grep `output_node_id\s*=` include `*.cc` | 命中集中在 `node_geo_repeat.cc`（gather_link_searches 建对时）与 versioning |
| 3 | 打开最热的文件看上下文 | 读 `node_geo_repeat.cc` L60-L120 | 看到 `RepeatZoneType::gather_link_searches` 里新建 Input 时 `input_storage.output_node_id = repeat_output.identifier;` |
| 4 | 反向验证读侧：谁消费它 | grep `output_node_id` include `*.cc`，排除写侧 | 命中 `node_tree_zones.cc` 建 zone、`geometry_nodes_lazy_function.cc` 装配期反查 Output、`node_layout_ex` 面板跨节点 |
| 5 | 用 git log 查演化 | `git log --oneline -S "output_node_id" -- source/blender/nodes/geometry/nodes/node_geo_repeat.cc` | 确认该写法自 Repeat 引入 commit 起就在（呼应 06 章"identifier 从诞生即存在"） |

五步走完，一个字段从"定义 → 写入 → 消费 → 历史"的全貌就出来了。这就是本篇方法论的标准用法：**每一跳都换一种检索方式，而不是把同一条 grep 换个词再跑一遍。**
