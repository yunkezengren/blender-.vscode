# 03 · 构建与运行验证

[前置知识总入口](../README.md) · [本章导航](README.md) · [上一篇](02-图导出与dot调试.md) · [下一章](../../重复区域-dsh/README.md)

> 基准：Blender `5.4.0-alpha`，本地工作树。本篇讲怎么把你在源码上做的改动跑起来、怎么用最小代价验证它没破坏语义。

## 先回答一个具体问题

你改了一行 `initialize_execution_graph`，怎么知道它没坏？

三条路，代价从低到高：

| 方式 | 代价 | 能验证什么 |
| --- | --- | --- |
| 静态检查（读代码 + 断言） | 分钟级 | 逻辑自洽、边界 |
| 单元测试（lf 框架有测试） | 十几分钟 | 函数级行为 |
| 完整构建 + 手动跑场景 | 数小时 | 端到端 |

本篇按这个顺序讲。

## 第一步：静态自查清单

`[讲解]` 在构建之前，先过一遍这类清单。它比构建快，能挡掉大部分低级错误：

| 检查项 | 判据 |
| --- | --- |
| 索引映射的长度 | `input_index_map.size() == 内层输入数` |
| 跳过的那一格 | `iterations` 是否真的不在内层图里 |
| 0 轮分支 | `iterations == 0` 时是否走到直通 |
| `output_was_set` 兜底 | 是否先查再设 |
| storage 生命周期 | 新加的对象是否放对层（scope vs storage） |
| 断言条件 | 是否与注释一致 |

`[讲解]` 其中"storage 放对层"最容易错。回忆第 04 章：跨求值的放 `ResourceScope`，单次求值的放 `RepeatEvalStorage`。如果放反：

- 该跨求值的放进了 storage → 每次求值重建，性能退化（甚至因为引用旧树而崩）；
- 该单次求值的放进了 scope → 多线程求值共享可变状态，数据竞争。

## 第二步：利用 lf 框架的测试

`[讲解]` Blender 的 `functions/` 模块有测试。位置：

```text
source/blender/functions/tests/
```

`[讲解]` 关键测试文件：

| 文件 | 测什么 |
| --- | --- |
| `FN_lazy_function_test.cc` | 惰性函数基本行为、partial evaluation、`output_was_set` |
| `FN_lazy_function_graph_test.cc` | 图构建、连线、执行 |
| `FN_multi_function_test.cc` | MultiFunction（与本系列关系较小） |

`[讲解]` 这些测试的价值：它们**不依赖 Blender 的完整 UI**，只测函数框架本身。所以：

1. 编起来快（模块级）；
2. 跑起来快（毫秒级）；
3. 断言明确（失败直接指出哪个断言）。

### 怎么跑

`[讲解]` Blender 的测试用 CTest 驱动。典型命令：

```bash
# 在构建目录
ctest -R lazy_function --output-on-failure
```

`[讲解]` 三个要点：

1. **`-R`**：按名字过滤，只跑匹配的测试；
2. **`--output-on-failure`**：失败才打印输出，成功时安静；
3. **构建目录**：必须在 `cmake --build` 产物的目录里跑。

如果你只想编译测试目标：

```bash
cmake --build . --target test_lazy_function
```

`[讲解]` 目标名可能带前缀（`test_`）。用 `cmake --build . --target help | grep lazy` 确认。

## 第三步：完整构建

`[讲解]` 只有前两步都过了，才值得花几小时完整构建。

### 最小化构建配置

`[讲解]` 关键：**关掉不需要的模块**能省大量时间。

```bash
cmake -S . -B build \
  -DWITH_CYCLES=OFF \
  -DWITH_OPENVDB=OFF \
  -DWITH_ALEMBIC=OFF \
  -DWITH_FFMPEG=OFF \
  -DWITH_AUDASPACE=OFF \
  -DCMAKE_BUILD_TYPE=Debug
```

`[讲解]` 几个取舍：

| 选项 | 关掉的影响 |
| --- | --- |
| `WITH_CYCLES=OFF` | 省最多时间；几何节点不受影响 |
| `WITH_OPENVDB=OFF` | 体素相关节点不可用，但 Repeat 不受影响 |
| `Debug` | 保留所有 `BLI_assert`——**调试必选** |

**注意 `Debug`**：`BLI_assert` 只在 Debug 构建里生效。Release 下断言消失，很多"框架误用"会变成静默的未定义行为。**验证语义时必须用 Debug**。

### 增量构建

`[讲解]` 改一个 `.cc` 后，增量构建通常几分钟。技巧：

1. **只改 `.cc` 不动 `.hh`**——动头文件会触发大量重编译；
2. **用 `ninja` 而不是 `make`**——依赖图更精确；
3. **`ccache`**：重复构建同一文件时命中缓存。

## 第四步：最小复现场景

`[讲解]` 构建完成后，不要急着打开复杂工程。做一个**最小场景**：

### Repeat 的验证场景

```text
场景：3 轮累加
  Repeat Input:
    Iterations = 3
    Value = 0（Float item）
  Repeat 体内:
    Value = Value + 1
  Repeat Output → Viewer
```

`[讲解]` 期望结果：Viewer 显示 3（0+1+1+1）。

**为什么这个场景好？**

1. **可手算**：每轮 +1，三轮就是 +3；
2. **能验证迭代数**：改成 0 应得 0，改成 5 应得 5；
3. **能验证串行**：如果串行链断了，结果会是 1（只有一轮生效）。

### 更细的验证点

`[讲解]` 同一个场景能验证四件事：

| 改什么 | 期望 | 验证了什么 |
| --- | --- | --- |
| Iterations = 0 | 0 | 直通分支 |
| Iterations = 1 | 1 | 单轮路径 |
| Iterations = 3 | 3 | 串行链 |
| 追加 border link（外部常量 10） | 13 | border link 扇出 |

## 第五步：交叉验证

`[讲解]` 单点验证不够。至少做两类交叉：

1. **数值 vs 图结构**：数值对，再导出 dot 看结构对不对（第 02 篇）；
2. **Debug vs Release**：Debug 下断言通过，Release 下行为一致——如果 Release 下崩了，说明有未定义行为被 Debug 断言遮住了。

## 调试的三种工具

`[讲解]` 构建完成后，三个调试抓手：

| 工具 | 用途 | 源码位置 |
| --- | --- | --- |
| `print_stack` | 打印完整上下文链 | `BLI_compute_context.hh` |
| `to_dot()` | 导出图结构 | `FN_lazy_function_graph.hh` L313 |
| `ScopedNodeTimer` | Profile 里的耗时条 | `NOD_geometry_nodes_lazy_function.hh` L550 |

`[讲解]` 三者的分工：

- **想知道"算到哪一轮了"** → `print_stack`；
- **想知道"图连对没"** → `to_dot`；
- **想知道"慢在哪"** → Profile 面板看 `ScopedNodeTimer` 记录的区间。

## 用 Python 脚本快速搭场景

`[讲解]` 手动点节点太慢。用 Python 脚本搭场景，几十行就能复现：

```python
import bpy

# 新建几何节点树
tree = bpy.data.node_groups.new("TestRepeat", "GeometryNodeTree")
tree.interface.new_socket("Geometry", in_out="INPUT", socket_type="NodeSocketGeometry")
tree.interface.new_socket("Geometry", in_out="OUTPUT", socket_type="NodeSocketGeometry")

# 建 Repeat 的一对节点
repeat_in = tree.nodes.new("GeometryNodeRepeatInput")
repeat_out = tree.nodes.new("GeometryNodeRepeatOutput")
repeat_in.inputs["Iterations"].default_value = 3
```

`[讲解]` 三个要点：

1. **`node_groups.new`** 的第二个参数是树类型，必须是 `"GeometryNodeTree"`；
2. **Repeat 的 Input/Output 必须配对**——Input 的 storage 里存 `output_node_id` 指向 Output；
3. **动态 socket 要手动加 item**——`repeat_out.repeat_items.new(...)`（具体 API 随版本变化，以实际为准）。

**优势**：脚本可重跑、可参数化。改迭代数只需改一行，不用手点。

## 反例与边界

### 反例 1：只在 Release 下测

断言消失后，索引越界可能"看起来正常"（读到垃圾值），换个场景就崩。

### 反例 2：用复杂工程验证

一改就出错，但说不清是哪一步坏的。**先最小场景过，再上复杂工程**。

### 反例 3：忘记清缓存

Blender 的节点树有运行时缓存（`zones()` 等）。改了树结构后如果没触发更新，可能看到旧结果。用 `tree.update_tag()` 或重新求值。

### 反例 4：以为增量构建一定正确

头文件改动后偶发"改了这个文件，行为却没变"——可能是构建系统漏了依赖。**改 `.hh` 后做一次全量或至少 `ninja -t clean` 相关目标**。

### 反例 5：跳过单元测试

`FN_lazy_function_test.cc` 里已经有"partial evaluation"这类复杂用例。自己写一遍既慢又容易漏。

## 对理解 Repeat 的帮助

`[讲解]` 本系列的正篇结论都可以用这套流程验证：

| 正篇结论 | 验证方式 |
| --- | --- |
| Iterations 永不被裁剪 | 0 轮场景输出直通，不是未定义 |
| 0 轮是直通 | Iterations=0 时输出 = 输入 |
| N 轮是串行链 | 累加场景结果 = N 次累加 |
| border link 扇出 | 外部常量改了，所有轮都看到新值 |
| 副作用强制 | Viewer 在第 2 轮，前 2 轮都执行 |

**最后一条值得单说**：把 Viewer 挂在第 2 轮的分支上，Iterations 设 5。观察 Profile：如果只执行了 0-2 轮（而不是 0-4），说明副作用机制生效了。
