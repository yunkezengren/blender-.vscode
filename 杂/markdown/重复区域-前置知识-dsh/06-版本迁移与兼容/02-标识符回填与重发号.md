# 02 · 标识符回填与重发号

[前置知识总入口](../README.md) · [本章导航](README.md) · [上一篇](01-versioning机制.md) · [下一篇](03-文件兼容不变量.md)

> 基准：Blender `5.4.0-alpha`，本地工作树。本篇讲 versioning 里最精细的一类操作：给老文件里的条目补上稳定标识符（`identifier`），并且保证重复执行不出错。主要源码：[`versioning_402.cc`](../../../source/blender/blenloader/intern/versioning_402.cc)（L1243-L1268）、[`versioning_500.cc`](../../../source/blender/blenloader/intern/versioning_500.cc)（L2399-L2428、L4445-L4473）。

## 先回答一个具体问题

一个老文件里的节点有 3 个 item，但那时还没有 `identifier` 字段。新代码依赖 `identifier` 做 socket 匹配。怎么补？

表面答案："从 0 开始编号就行"。

`[讲解]` 但这个简单答案里有三个坑：

1. **必须幂等**——versioning 可能跑多次（保存后重开又跑一次），不能重复分配；
2. **不能与已有冲突**——有些文件可能已经部分迁移过；
3. **`next_identifier` 要跟上**——否则新建 item 时会撞号。

本篇就讲这三个坑怎么填。

## 范式一：幂等检查 + 重新发号

`[讲解]` 看 `versioning_402.cc` 的 Capture Attribute 节点迁移（L1243-L1268）：

```cpp
if (!MAIN_VERSION_FILE_ATLEAST(bmain, 402, 50)) {
  for (bNodeTree &ntree : bmain->nodetrees) {
    if (ntree.type != NTREE_GEOMETRY) {
      continue;
    }
    for (bNode &node : ntree.nodes) {
      if (node.type_legacy != GEO_NODE_CAPTURE_ATTRIBUTE) {
        continue;
      }
      if (!version_node_ensure_storage_or_invalidate(node)) {
        continue;
      }
      NodeGeometryAttributeCapture *storage = static_cast<NodeGeometryAttributeCapture *>(
          node.storage);
      if (storage->next_identifier > 0) {
        continue;
      }
      storage->capture_items_num = 1;
      storage->capture_items = MEM_new_array<NodeGeometryAttributeCaptureItem>(
          storage->capture_items_num, __func__);
      NodeGeometryAttributeCaptureItem &item = storage->capture_items[0];
      item.data_type = storage->data_type_legacy;
      item.identifier = storage->next_identifier++;
      item.name = BLI_strdup("Value");
    }
  }
}
```

`[讲解]` 逐段拆：

### 第一层：版本门槛

```cpp
if (!MAIN_VERSION_FILE_ATLEAST(bmain, 402, 50)) {
```

`[讲解]` 语义："如果文件版本**早于** 4.2.50，就执行迁移"。

**为什么是 402, 50 而不是 402, 0？**

因为迁移本身可能在某个 patch 版本引入或修正。用精确的 patch 号能避免"已经在 4.2.30 迁移过的文件再迁移一次"。

`[讲解]` 这个宏的语义要记牢：**文件版本必须"至少"达到某值才跳过迁移**。所以 `!ATLEAST` = "文件比这个版本老"。

### 第二层：遍历所有节点树

```cpp
for (bNodeTree &ntree : bmain->nodetrees) {
  if (ntree.type != NTREE_GEOMETRY) { continue; }
  for (bNode &node : ntree.nodes) {
    if (node.type_legacy != GEO_NODE_CAPTURE_ATTRIBUTE) { continue; }
```

`[讲解]` 三层过滤：

1. 遍历 `bmain->nodetrees`（主数据库里所有节点树）；
2. 只要几何节点树（`NTREE_GEOMETRY`）；
3. 只要 Capture Attribute 类型。

**注意 `bmain->nodetrees`**：这是全局遍历，不只是当前场景。因为一个文件可能含大量节点树资源。

### 第三层：存储保险

```cpp
if (!version_node_ensure_storage_or_invalidate(node)) {
  continue;
}
```

`[讲解]` 这个函数保证节点的 storage 已分配。**为什么需要？** 老文件的 storage 可能是 nullptr（某些罕见的损坏或特殊构造）。

如果不检查就 `static_cast<...>(node.storage)` 会解引用空指针。

`[讲解]` 名称里的 `or_invalidate` 说明它可能"让这个节点失效"（而不是崩溃）——这是防御式设计的典型。

### 第四层：幂等检查（关键）

```cpp
if (storage->next_identifier > 0) {
  continue;
}
```

`[讲解]` **这一行是整个迁移的核心**。

逻辑：`next_identifier > 0` 意味着"已经分配过至少一个 identifier"，说明这个文件已经迁移过。跳过。

`[讲解]` 为什么不检查 `items_num > 0`？

因为 `items_num` 可能因为其他原因非零（比如用户手动删光了 item 但 `next_identifier` 仍是最大值）。`next_identifier` 是**单调递增**的，它 > 0 就一定代表"曾经分配过"，是更可靠的"是否迁移过"的判据。

### 第五层：重建数据

```cpp
storage->capture_items_num = 1;
storage->capture_items = MEM_new_array<NodeGeometryAttributeCaptureItem>(
    storage->capture_items_num, __func__);
NodeGeometryAttributeCaptureItem &item = storage->capture_items[0];
item.data_type = storage->data_type_legacy;
item.identifier = storage->next_identifier++;
item.name = BLI_strdup("Value");
```

`[讲解]` 五步：

| 步 | 动作 | 说明 |
| --- | --- | --- |
| 1 | 设 `items_num = 1` | 老版本是"单一捕获"，对应一个 item |
| 2 | 分配数组 | `MEM_new_array` |
| 3 | 取引用 | 简化后续写法 |
| 4 | 从 `data_type_legacy` 复制类型 | 老字段迁移到新结构 |
| 5 | **`identifier = next_identifier++`** | 分配标识符 |
| 6 | `name = BLI_strdup("Value")` | 默认名字 |

`[讲解]` 第 5 步的细节：`next_identifier++` 是**后缀自增**，所以：

- `item.identifier` 得到旧值（0）；
- `next_identifier` 变成 1。

**结果**：item 的 id 是 0，`next_identifier` 是 1——下次新建 item 会得到 id 1，不冲突。

## 范式二：手写重建 + 显式收尾

`[讲解]` 看 `versioning_500.cc` 的 Viewer 节点迁移（L2399-L2428）。结构类似，但做法更明确：

`[讲解]` 关键差异：**结尾显式设置 `next_identifier`**。

```cpp
/* 伪代码示意，实际见源码 */
storage->items_num = 2;
storage->items = MEM_new_array<NodeViewerItem>(2, __func__);
storage->items[0].identifier = 0;
storage->items[1].identifier = 1;
storage->next_identifier = 2;   /* ← 显式收尾 */
```

`[讲解]` 两种写法的对比：

| 写法 | 优点 | 缺点 |
| --- | --- | --- |
| `identifier = next_identifier++` | 不会忘记同步 | 需要初始 `next_identifier = 0` |
| 显式设置每个 id + 显式设 `next_identifier` | 意图明确 | 容易忘记最后一行 |

`[讲解]` **第二种更容易出错**：如果写了 `items[0].identifier = 0`、`items[1].identifier = 1` 却忘了 `next_identifier = 2`，下次新建 item 会得到 id 0 或 1（取决于原值）——**撞号**。

## 范式三：清除无效标记

`[讲解]` 看 `versioning_500.cc` 的 Repeat 相关迁移（L4445-L4473）。

`[讲解]` 这类操作不涉及 identifier，而是清除某些字段。Repeat 的具体内容是把 Repeat Input/Output 加入 `no_muting_nodes` 并清 `NODE_MUTED` 标志。

```cpp
/* 伪代码示意 */
for (bNode &node : ntree.nodes) {
  if (node.type_legacy == GEO_NODE_REPEAT_INPUT ||
      node.type_legacy == GEO_NODE_REPEAT_OUTPUT) {
    node.flag &= ~NODE_MUTED;
  }
}
```

`[讲解]` **为什么要清 MUTED？**

在某个版本之前，Repeat 的接口节点可以被用户静音（mute）。但静音一个 zone 的输入/输出节点在语义上**没有意义**——zone 就不成立了。

所以新版本禁止静音（注册时设 `no_muting = true`），并且迁移时清掉历史遗留的 MUTED 标志。

`[讲解]` 这是一类重要的迁移：**当某个操作在新版本变成非法时，要清理老数据里的非法状态**。

## 三个坑的完整解法

`[讲解]` 回到开头的问题，现在能完整回答：

### 坑 1：幂等

解法：`if (storage->next_identifier > 0) continue;`

**为什么这个判据可靠？**

- `next_identifier` 单调递增，永不减小；
- 新建节点时初始为 0；
- 分配过就 > 0。

**反例**：如果判据用 `items_num == 0`，那么"用户删光所有 item"的老文件会被误判为"未迁移"，重新分配 id——但 `next_identifier` 已经是 N，新分配的 id 从 N 开始，不会撞号但会浪费。更糟的是如果迁移逻辑是"重建 items"，会把用户的删除意图覆盖掉。

### 坑 2：不与已有冲突

解法：始终从 `next_identifier` 分配，不用固定值。

**错误做法**：

```cpp
item.identifier = 0;   /* 硬编码，如果已有 id 0 就撞了 */
```

**正确做法**：

```cpp
item.identifier = storage->next_identifier++;
```

### 坑 3：next_identifier 要跟上

解法：用后缀自增，或用显式收尾。

**判据**：迁移结束时，`next_identifier` 必须等于"所有已有 id 的最大值 + 1"。

## 用小数据走一遍

`[讲解]` 文件版本 4.2.20，一个 Capture Attribute 节点，`next_identifier = 0`（该字段刚引进，全是 0）。

**迁移前**：

```text
node.storage:
  data_type_legacy = SOCK_FLOAT
  capture_items    = nullptr
  capture_items_num = 0
  next_identifier  = 0
```

**第 1 次迁移**：

| 步 | 检查/动作 | 结果 |
| --- | --- | --- |
| 1 | `!ATLEAST(402, 50)` | true（4.20 < 4.50）→ 继续 |
| 2 | `next_identifier > 0` | false（=0）→ 继续 |
| 3 | `capture_items_num = 1` | 1 |
| 4 | 分配数组 | 地址 0xA000 |
| 5 | `item.data_type = SOCK_FLOAT` | — |
| 6 | `item.identifier = next_identifier++` | id=0, next=1 |
| 7 | `item.name = "Value"` | 堆字符串 |

**迁移后**：

```text
node.storage:
  capture_items     = 0xA000
  capture_items_num = 1
  next_identifier   = 1
  items[0] = { data_type: SOCK_FLOAT, identifier: 0, name: "Value" }
```

**第 2 次迁移（重开文件）**：

| 步 | 检查 | 结果 |
| --- | --- | --- |
| 1 | `!ATLEAST(402, 50)` | **false**（文件现在是 4.2+ 版本）→ 整体跳过 |

`[讲解]` 注意第一层就挡住了——因为保存后文件版本升级了。

**那幂等检查还需要吗？** 需要。考虑这种情况：文件是 4.2.20 保存的，但**没有保存就切换了工作区**（versioning 在内存里跑过，但没有写盘）。再次打开同一个老文件时，versioning 会再跑一次。此时 `next_identifier` 已经是 1（内存里的），但文件版本仍是老的——第 1 层挡不住，只能靠第 3 层。

`[讲解]` 这就是两个检查的分工：

- **版本检查**（第 1 层）：挡"已保存的新文件"；
- **幂等检查**（第 3 层）：挡"迁移过但没保存"。

**两层缺一不可**。

## 反例与边界

### 反例 1：只靠版本检查

场景：迁移后崩溃、未保存。重开老文件，版本仍是老的，versioning 再跑一次——没有幂等检查就重复分配。

### 反例 2：只靠幂等检查

场景：新版本需要**再次**迁移（比如修正了上一次的错误）。如果只有幂等检查，第二次迁移会被误跳过。所以版本门槛必须精确到 patch 号。

### 反例 3：用 `items_num > 0` 作幂等判据

用户删光 item 后 `items_num` 是 0，会被误判为未迁移。

### 反例 4：忘记更新 `next_identifier`

新建 item 得到重复 id，socket 匹配错乱——这是最隐蔽的 bug（不崩，只是行为错）。

### 反例 5：在迁移里改 DNA 布局

versioning 只处理**数据**，不处理**布局**。加字段是 DNA 的事（自动兼容），不是 versioning 的事。

### 反例 6：迁移顺序有依赖却没排序

如果两个迁移互相依赖（A 的产出是 B 的输入），必须按正确顺序执行。源码里通过版本号大小保证顺序（先旧后新）。

## 对理解 Repeat 的帮助

`[讲解]` Repeat 本身**没有**自己的 identifier 回填迁移——因为 `NodeRepeatItem::identifier` 从引入时就存在。

但**范式**是共通的：

| 迁移对象 | 用的是哪个范式 | 与本篇的对应 |
| --- | --- | --- |
| Capture Attribute（402） | 范式一（幂等+重发号） | 与本篇完全相同 |
| Viewer（500） | 范式二（显式收尾） | 同上 |
| Repeat（500） | 范式三（清标记） | 不同类，但同样是"清理非法状态" |

`[讲解]` 正篇 02-02 引用这三处时说的是"模式与 Repeat 同源"。读完本篇就明白：**同源指的是"重复问题"同源**——任何"新增稳定标识符"的迁移都会遇到这三个坑。
