# 07 · 执行钩子与副作用接口

[前置知识总入口](../README.md) · [本章导航](README.md) · [上一篇](06-GraphExecutor调度机制.md) · [下一章](../02-参数转发与上下文/README.md)

> 基准：Blender `5.4.0-alpha`，本地工作树。本篇讲 `GraphExecutor` 的三个钩子基类——它们是惰性执行框架留给外部"插入行为"的全部入口。主要源码：[`FN_lazy_function_graph_executor.hh`](../../../source/blender/functions/FN_lazy_function_graph_executor.hh) L25-L89。

## 先回答一个具体问题

执行器明明可以直接调 `fn.execute`，为什么要留一个 wrapper 钩子？

源码注释回答了这个问题（graph_executor.hh L75-L79）：

> "Can be used to pass extra context into the execution of a function. The main alternative to this is to create a wrapper `LazyFunction` for the `FunctionNode`s. Using this light weight wrapper is preferable if possible."

`[讲解]` 这句话是理解整个钩子体系的钥匙。它说的是一次**架构取舍**：

| 方案 | 做法 | 成本 |
| --- | --- | --- |
| A. 包装 LazyFunction | 为每个需要额外行为的节点，造一个新的 `LazyFunction` 子类包一层 | N 个对象、N 份接口定义 |
| B. 执行钩子 | 保留原 `LazyFunction`，用钩子拦截"即将执行"这个时刻 | 1 个钩子对象、每次执行多一次虚函数调用 |

Blender 选了 B。Repeat Zone 是这个取舍的最佳样本：**如果选 A，N 轮迭代就要造 N 个 LazyFunction 对象**；选 B 只多一个 wrapper，每次执行多一次哈希查找。

## 三个钩子

`GraphExecutor` 有三个可选钩子，全部可为 `nullptr`：

```cpp
const Logger *logger_;                                  // 日志
const SideEffectProvider *side_effect_provider_;        // 副作用
const NodeExecuteWrapper *node_execute_wrapper_;        // 执行包装
```

`[讲解]` 三者的分工：

| 钩子 | 调用时机 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| `Logger` | 执行前后、值产生时 | 记录事件 | 改变执行结果 |
| `SideEffectProvider` | 执行开始前 | 声明"哪些节点必须跑" | 改变节点身份 |
| `NodeExecuteWrapper` | 每个节点执行前 | 换 Context、加计时、改行为 | 改节点的接口定义 |

## 钩子一：NodeExecuteWrapper

```cpp
class GraphExecutorNodeExecuteWrapper {
 public:
  virtual ~GraphExecutorNodeExecuteWrapper() = default;

  /**
   * Is expected to run `node.function().execute(params, context)` but might do some extra work,
   * like adjusting the context.
   */
  virtual void execute_node(const FunctionNode &node,
                            Params &params,
                            const Context &context) const = 0;
};
```

`[讲解]` 逐项拆解：

**1. 纯虚，必须实现。** 不像其他两个钩子有默认实现。

**2. 契约是"你负责执行这个节点"**。注释说 "Is expected to run `node.function().execute(params, context)`"。这意味着实现**必须**最终调到原函数，否则节点永远不执行。

**3. "might do some extra work, like adjusting the context"**。这是全部灵活性的来源：可以换 context、加计时、改参数——但最终要回到原来的 execute。

### Repeat 的实现

`RepeatBodyNodeExecuteWrapper`（正篇 04-02 详讲）是教科书级用法：

```cpp
void execute_node(const lf::FunctionNode &node,
                  lf::Params &params,
                  const lf::Context &context) const override
{
  GeoNodesUserData &user_data = *static_cast<GeoNodesUserData *>(context.user_data);
  const int iteration = lf_body_nodes_->index_of_try(const_cast<lf::FunctionNode *>(&node));
  const LazyFunction &fn = node.function();
  if (iteration == -1) {
    /* 不是 body 节点，正常执行 */
    fn.execute(params, context);
    return;
  }
  /* 是 body 节点：换一个带 iteration 的 context */
  bke::RepeatZoneComputeContext body_compute_context{...};
  GeoNodesUserData body_user_data = user_data;
  body_user_data.compute_context = &body_compute_context;
  ...
  fn.execute(params, body_context);
}
```

`[讲解]` 两种路径：

- **非 body 节点**（`iteration == -1`）：原样执行。这是"钩子必须放行其他节点"的体现——一个 wrapper 拿到的是**全部**节点的执行权，不能只顾自己关心的那些。
- **body 节点**：换 context 后执行。

**为什么用 wrapper 而不是 N 个 LazyFunction**：N 个 body 节点共享同一个 `body_fn_.function`。如果为每轮造一个 LazyFunction，就要复制 N 份函数对象（每份含接口定义、可能的 storage 逻辑）。wrapper 方案只有 1 个，每次执行多一次 `index_of_try`（O(1) 哈希查找）。

## 钩子二：SideEffectProvider

```cpp
class GraphExecutorSideEffectProvider {
 public:
  virtual ~GraphExecutorSideEffectProvider() = default;
  virtual Vector<const FunctionNode *> get_nodes_with_side_effects(const Context &context) const;
};
```

`[讲解]` 这个接口回答一个问题：**在当前上下文下，哪些节点即使输出没人要，也必须执行？**

### 什么叫副作用

在纯函数世界里，"输出没人要"= "不用算"。但有副作用时这个等式不成立：

| 副作用类型 | 例子 | 为什么必须执行 |
| --- | --- | --- |
| 外部可见输出 | Viewer 节点 | 用户要看值 |
| 持久状态改变 | Store Named Attribute | 数据写进几何 |
| 诊断信息 | Warning 节点 | 用户要看警告 |
| 调试探针 | 日志 | 开发要看 |

`[讲解]` 注意"Store Named Attribute"这一行：它既是"写属性"（有副作用），也可能有输出（被使用）。但即使输出没人要，写属性这件事也必须发生——否则用户设置的属性不会生效。

### 返回值语义

返回 `Vector<const FunctionNode *>`：这些节点的**输出被强制标记为 Used**，从而被拉进执行。

`[讲解]` 两个细节：

1. **返回的是节点不是 socket**。因为"这个节点有副作用"通常意味着"它的全部输出都要算"（或者至少它的执行必须发生）。
2. **每次执行都可能不同**。接口带 `const Context &context` 参数，因为"哪些节点有副作用"取决于当前上下文——比如 Viewer 只在用户查看的那一轮需要执行。

### 默认实现

基类有默认实现（返回空 vector）。所以不配 provider = 没有副作用 = 纯函数语义。

### 两层 provider

几何节点里有两层：

| 层 | 类型 | 查什么表 |
| --- | --- | --- |
| 外层 | `GeometryNodesLazyFunctionSideEffectProvider` | `nodes_by_context`（整树） |
| 内层 | `RepeatZoneSideEffectProvider` | `iterations_by_iteration_zone`（按迭代号） |

`[讲解]` 为什么要两层？因为**同一份循环体图对应 N 个上下文**。外层只知道"这个 zone 有副作用"，内层才知道"是第 5 轮有副作用"。

看 `GeoNodesSideEffectNodes` 的两张表：

```cpp
struct GeoNodesSideEffectNodes {
  MultiValueMap<ComputeContextHash, const lf::FunctionNode *> nodes_by_context;
  MultiValueMap<std::pair<ComputeContextHash, int32_t>, int> iterations_by_iteration_zone;
};
```

`[讲解]` 两张表的分工：

- `nodes_by_context`：键是上下文哈希，值是节点列表。回答"这个上下文下哪些节点有副作用"。
- `iterations_by_iteration_zone`：键是 (上下文哈希, zone 输出节点 id)，值是迭代号。回答"这个 zone 的第几轮需要执行"。

**为什么分开？** 因为 zone 的副作用是**按轮次定位**的：用户可能只查看第 3 轮，那就只有第 3 轮需要强制执行。普通节点的副作用是**整体**的，不需要轮次。

## 钩子三：Logger

```cpp
class GraphExecutorLogger {
 public:
  virtual ~GraphExecutorLogger() = default;

  virtual LoggingEnabledState get_logging_enabled_state(const Context &context) const;
  virtual void log_socket_value(const Socket &socket, ...) const;
  virtual void log_before_node_execute(const FunctionNode &node, ...) const;
  virtual void log_after_node_execute(const FunctionNode &node, ...) const;
  virtual void dump_when_outputs_are_missing(const FunctionNode &node, ...) const;
  virtual void dump_when_input_is_set_twice(const InputSocket &target_socket, ...) const;
};
```

`[讲解]` 六个回调，分三类：

| 类别 | 回调 | 用途 |
| --- | --- | --- |
| 门控 | `get_logging_enabled_state` | 决定本次执行要不要记日志 |
| 事件 | `log_before_node_execute` / `log_after_node_execute` | 节点执行前后 |
| 值 | `log_socket_value` | 值产生时 |
| 诊断 | `dump_when_outputs_are_missing` / `dump_when_input_is_set_twice` | 异常时转储 |

**`get_logging_enabled_state` 为什么存在？** 日志有成本。如果用户没开"查看值"，不该记。这个回调让执行器可以在开跑前就问"要记吗"，避免每个节点都问一次。

**两个 `dump_when_*` 是诊断用**。当执行器发现"某节点该设的输出没设"或"某输入被设了两次"时，调用它们输出上下文，便于定位 bug。这两个在 Debug 构建里对排查框架误用非常有用。

## 钩子在执行器里的调用点

`[讲解]` 三个钩子的调用时机散落在 `generic_graph_executor` 里。关键点位：

| 时机 | 调用 |
| --- | --- |
| 执行开始 | `logger->get_logging_enabled_state()` |
| 执行开始 | `side_effect_provider->get_nodes_with_side_effects()` |
| 每个节点执行前 | `node_execute_wrapper->execute_node()` |
| 节点执行前后 | `logger->log_before/after_node_execute()` |
| 值产生 | `logger->log_socket_value()` |
| 异常 | `logger->dump_when_*()` |

`[讲解]` 注意 `side_effect_provider` 只在**开始**调一次。这意味着"执行过程中不会动态发现新的副作用节点"。这是简化——如果允许中途改变，调度器就要反复重算需求图。

## 三者的协作：Repeat 的完整链路

一个 Repeat 区域挂了一个 Viewer 在第 2 轮（共 5 轮）：

```text
1. 外层执行器启动，调 GeometryNodesLazyFunctionSideEffectProvider
   → 查 nodes_by_context，发现 Repeat zone 节点有副作用
   → 同时查出 iterations_by_iteration_zone[(hash, zone_id)] = {2}
2. 执行到 Repeat zone 节点
3. RepeatEvalStorage 首次构建内层图（5 个 body 节点）
4. 装配内层 GraphExecutor，传入 RepeatZoneSideEffectProvider
5. 内层执行器启动，调 RepeatZoneSideEffectProvider
   → 查表得 {2}，翻译成 body[2] 的节点指针
   → 返回 [body[2]]
6. 执行器把 body[2] 标记为"必须执行"
7. 因为串行依赖，body[0]..body[2] 依次执行
8. body[3]、body[4] 按正常需求传播决定（没人要输出 → 跳过）
9. 每轮执行时，RepeatBodyNodeExecuteWrapper 注入带 iteration 的 context
10. Viewer 在第 2 轮记下值
```

`[讲解]` 这个链路展示了三个钩子的**精确分工**：

- **provider 决定"谁必须跑"**（body[2]）；
- **wrapper 决定"用什么身份跑"**（iteration=2 的 context）；
- **logger 决定"记什么"**（Viewer 值）。

**缺一不可**。没有 provider，body[2] 可能被跳过（因为输出没人要）；没有 wrapper，所有轮次的日志会混在一起（因为没有轮次身份）。

## 反例与边界

### 反例 1：以为输出未使用就能裁剪带副作用的体

Provider 的存在就是为了解决这个。如果忘了配 provider，Viewer 在未使用的分支上就不会执行。

### 反例 2：以为 wrapper 可以改变节点身份

Wrapper 只能改 context，不能改 `node` 本身。节点的 `function()` 是固定的。

### 反例 3：以为 provider 每轮都问

只在执行开始时问一次。所以副作用表必须在执行前就填好。

### 反例 4：以为 logger 影响执行结果

日志是只读观察。但注意：如果 logger 的实现里有 bug（比如写错内存），确实会影响——但那是实现 bug，不是接口设计。

### 反例 5：以为三个钩子必须全配

全部可选。只配需要的。Repeat 配了全部三个（它有日志需求、副作用需求、上下文需求）。

### 反例 6：以为 wrapper 可以跳过节点执行

契约要求最终调到 `fn.execute`。跳过会导致下游永远等待。

## 对理解 Repeat 的帮助

本篇是 01 章的收尾，把七篇串起来：

| 篇 | 主题 | 在 Repeat 中的体现 |
| --- | --- | --- |
| 01 | 惰性求值模型 | 按需执行、副作用强制 |
| 02 | LazyFunction 接口 | `LazyFunctionForRepeatZone` 的类骨架 |
| 03 | Params 调用约定 | `execute_impl` 里的 get_input/set_output |
| 04 | ValueUsage | Iterations 必须 Used |
| 05 | lf::Graph | 展开图的数据结构 |
| 06 | GraphExecutor | 内层图由谁驱动 |
| **07** | **执行钩子** | **wrapper + provider 的双层结构** |

**最关键的一条**：Repeat Zone 之所以能"正确记录每一轮的值、正确地在指定轮强制执行"，靠的不是把循环体复制 N 份函数对象，而是**一个共享的函数 + 一个轻量 wrapper + 一个按轮次定位的 provider**。这个设计正是总览篇说的"wrapper 方案优于每轮独立 LazyFunction"的具体体现。
