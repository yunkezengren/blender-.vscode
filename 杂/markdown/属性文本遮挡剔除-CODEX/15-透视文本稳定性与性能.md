# 透视文本稳定性与性能

> 本章记录局部平面补偿的原理、性能边界，以及随后进行的代码整理。
> 用户已反馈透视旋转时的文本消失问题似乎得到解决；这属于场景复测反馈，尚非所有场景的保证。
> 前面章节保留较早提交的快照，本章描述其后的工作区实现。

## 1. 为什么点可见，文字却会消失

原判断把文字锚点投影到屏幕，用整数坐标读取一个深度像素。
GPU 深度通常对应像素中心，而锚点可以落在像素内部任意位置。
在倾斜表面上，这两处的深度本来就不同。

视图旋转时，锚点连续移动，选中的像素会离散地变化。
深度差一旦越过原来的固定容差，文本的可见性就会翻转。
近距离透视视图中，这种采样位置差异尤其容易暴露。

这次改动针对采样位置差异。
它没有使用跨帧可见性缓存，也没有增加 GPU 深度回读次数。

## 2. 方法：局部平面重建

两个数学事实需要同时理解：

1. 透视深度相对于观察空间距离是非线性的。
2. 同一个投影三角形的窗口深度，相对于屏幕坐标是仿射的。

因此可以通过邻近像素推算同一表面在锚点位置的深度。

```text
锚点处表面深度 = 像素中心深度
               + 横向深度变化 × 横向偏移
               + 纵向深度变化 × 纵向偏移
```

代码中的 `sx` 和 `sy` 分别为横、纵采样方向，取 `-1` 或 `1`。
`step_x`、`step_y` 是沿对应方向移动一像素产生的深度增量。
`dx`、`dy` 是锚点相对于中心像素中心的偏移。

```text
reconstructed = center + step_x × dx × sx + step_y × dy × sy
```

例如锚点比像素中心向右偏移 0.4 像素，表面每向右一像素深度增加 0.002，
那么横向补偿为 0.0008。
这个值明显超过原有 0.00002 容差，但它可以完全来自表面倾斜。
只扩大统一容差，会同时放松所有物体的遮挡判断；局部重建则使用当前表面的变化量。

## 3. 为什么检查 3×3 样本

相邻像素不一定来自同一个表面。
如果左边是前景，右边是背景，两者之间的深度跳变不能直接解释为表面斜率。

每个候选平面都要检查该象限的 3×3 样本：

- 样本不能是清除后的背景深度 `1.0`。
- 样本深度必须接近候选平面的预测值。
- 平面一致性容差为 `2e-6`。
- 候选采样范围必须完整位于图像内部。

2×2 样本不足以排除某些沿单轴变化的深度阶跃。
三个连续样本能检查变化是否持续符合相同斜率。
这仍是局部几何近似，不能证明像素一定属于同一对象。

## 4. 为什么有四个象限

折角附近的不同方向可能落在不同面上。
算法尝试左下、右下、左上、右上四个候选区域。
某个方向不满足平面关系时，另一个方向仍可能提供有效表面。

每个区域包含中心像素及同侧的两行、两列样本。
四个区域的并集位于中心周围的 5×5 范围内。
这不是取 5×5 或 3×3 中最远的深度；使用的是通过验证的平面预测值。

## 5. 性能开销

执行路径具有提前退出：

| 条件 | 操作 |
|---|---|
| 关闭遮挡选项 | 不执行文字深度测试 |
| 单像素判断已可见 | 直接显示，不执行邻域检查 |
| 正交视图 | 只使用单像素判断 |
| 透视且初判遮挡 | 尝试局部平面补偿 |
| 某象限越界 | 跳过该象限 |
| 平面预测仍然遮挡 | 跳过该象限的完整一致性检查 |
| 某样本不符合平面 | 提前结束当前候选检查 |
| 找到有效可见候选 | 立即返回可见 |

每次补偿最多尝试四个象限，每个完整检查九个样本。
还要读取估算斜率所需的横、纵邻居；部分样本会重复读取。
这些是已回读到 CPU 内存的数组读取和标量运算。
没有额外发起 GPU 回读，没有遍历网格，也没有实现实例。

若文字锚点数量为 N，总复杂度仍为 O(N)，每个锚点的额外工作有固定上限。
这并不意味着成本为零：大量文本同时进入补偿分支时，CPU 帧时仍可能增加。
目前没有实际用户场景的前后帧时对比，不能给出可靠百分比。
性能测量应分别记录总文字数、进入补偿的比例和文本绘制阶段耗时。
多行属性会形成多条缓存文字，因此复杂度里的 N 指缓存文字条目数。

## 6. 为什么只对透视视图启用

用户反馈正交视图没有出现同样明显的闪烁。
当前代码通过 `rv3d->is_persp` 控制补偿，仅透视视图启用。
该标记表达实际投影类型，也适用于相机视图中的投影选择。
正交视图保留原有单像素判断。

正交投影理论上也可能出现像素采样位置误差。
当前限制基于已观察到的问题范围，不能理解为正交视图绝不会出现误差。

## 7. 函数与常量

| 名称 | 职责 |
|---|---|
| `text_anchor_project_with_depth()` | 计算锚点的屏幕位置和窗口深度 |
| `text_depth_is_occluded()` | 统一单像素比较和背景处理 |
| `text_anchor_is_occluded_perspective()` | 验证局部平面并补偿透视采样偏差 |
| `text_depth_bias` | 最终深度比较容差，保持 `2e-5` |
| `text_depth_plane_tolerance` | 平面一致性容差，保持 `2e-6` |

两个容差含义不同，不应为了调节可见性而同时修改。
平面检查限制的是拟合残差，不限制斜率本身。
这避免了旧实验在近距离陡斜面上因为斜率超过固定上限而失去补偿资格。

## 8. 本次代码风格整理

- 将深度比较与容差集中定义，避免透视和正交分支分别维护相同规则。
- 修正深度缓存的注释：实际是在 prepass 之后、grid 绘制之前刷新。
- 缓存尺寸直接使用 `ViewDepths::w/h`，移除重复成员。
- 缓存成员放回成员声明区域，更新函数与其他绘制函数放在一起。
- 只读的深度需求查询使用 `const DRWTextStore *`。
- 实例包围盒的射线参数改名为 `exit_t`，明确它是从内部向相机方向的出口。
- 说明透视射线没有归一化，因此 `t = 1` 对应相机位置。
- 简化 UI 属性调用，提示文字使用 scene geometry 描述遮挡来源。
- 使用项目指定的 clang-format 格式化当前分支修改过的 C/C++ 行。

## 9. 验证边界

此前从实际源码抽取函数运行的 34 项数值检查已通过，覆盖斜面、遮挡、背景、阶跃和边界。

这些证据不能替代所有复杂场景的视觉回归。

没有可靠候选时，代码保留原始遮挡结论。

## 10. 开关命名统一

原来的 `Exclude Backfaces` 描述的是背面剔除，但实际依据是场景深度。
现统一为 UI `Occlusion Culling`、RNA `viewer_text_occlusion_culling`、
DNA `V3D_OVERLAY_VIEWER_TEXT_OCCLUSION_CULLING` 与同名 State 查询。
DNA 仍使用位 `1 << 20`，已有文件保存的开关状态继续生效。
RNA 属性标识改名后，引用旧 Python 属性名的脚本需要使用新名称。
