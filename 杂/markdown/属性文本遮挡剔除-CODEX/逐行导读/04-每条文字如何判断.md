# 第四站：每条文字怎样被投影、判断并绘制

> 文件：`draw_manager_text.cc`，也是本分支深度方案的消费端。
> 读完能手算一个像素为什么显示或剔除，并理解透视视图的局部平面补偿。

## 1. `ViewCachedString` 与 `DRWTextStore`

`ViewCachedString` 是一条缓存文字：`vec[3]` 是三维锚点，`col` 是颜色，`sco[2]` 是投影后的屏幕短整数坐标，`xoffs/yoffs` 是二维文字布局偏移，`flag` 装坐标空间和遮挡位，`str` 指向文字内容。文字是否可见由 `sco[0]` 是否为 `IS_CLIPPED` 表示。

`DRWTextStore` 保存 `Vector<ViewCachedString>` 和字符串分配器。本分支增添 `const ViewDepths *depths = nullptr`。`const` 表示绘制代码不能通过指针改写深度；该指针借自 Overlay `Instance`，并不拥有缓冲。

`DRW_text_cache_add` 在生产阶段写入 `ViewCachedString`，还根据 `DRW_TEXT_CACHE_STRING_PTR` 决定是借用字符串还是复制字符串。属性数值转出来的局部字符数组通常要复制进 allocator，不能让缓存保留已经离开作用域的栈地址。

## 2. 两次投影各做什么

`DRW_text_cache_draw` 原有 `ED_view3d_project_short_ex` 负责判断裁剪、局部裁剪与屏幕位置，并把整数屏幕坐标写入 `vos.sco`。它沿用 Blender 已有的投影和裁剪路径。

新增 `text_anchor_project_with_depth` 再投影一次，保留浮点屏幕 `(x,y)` 和 `[0,1]` 深度。它只在有可用深度、且该条文字带遮挡位时调用。两次投影有重复算术，但返回数据职责不同：前者做原有裁剪与最终文字坐标，后者提供深度比较所需的精确浮点位置。此结构有优化空间，但本分支先保持原裁剪行为。

`persmat` 的选择取决于 `DRW_TEXT_CACHE_GLOBALSPACE`：世界坐标使用 `rv3d->persmat`，本地坐标使用 `rv3d->persmatob`。用错矩阵会导致读取的深度像素与文字实际位置不一致。

## 3. 从三维点到深度

函数先把 `(x,y,z)` 扩为齐次向量 `(x,y,z,1)`，乘以投影矩阵得到 `vec4`。`w = abs(vec4[3])` 是透视除法所用的量；零值不能做除法。`vec4[2] <= -w || vec4[2] >= w` 排除裁剪深度范围以外的点。

屏幕坐标：

```text
fx = width / 2 × (1 + clip_x / w)
fy = height / 2 × (1 + clip_y / w)
```

超出视口范围则返回 `false`。深度先算 `ndc_z = clip_z / w`，再转换为 `depth = (ndc_z + 1) / 2`。透视投影下，深度对观察空间距离并不线性；但深度缓冲和 CPU 比较都使用同一 `[0,1]` 窗口深度约定。

## 4. 深度数组如何索引

`x = int(xy[0])`、`y = int(xy[1])` 选中锚点落入的像素。先检查 `x/y` 是否位于 `ViewDepths::w/h`，再取 `depths[y * w + x]`。这就是二维图像以一维逐行数组存储的常见公式：先跳过 `y` 行，每行 `w` 个元素，再横向偏移 `x`。

投影失败或深度下标越界时，把 `vos.sco[0]` 设为 `IS_CLIPPED` 并继续下一条。这里不尝试读取越界内存。

## 5. 单像素基础判断

```text
occluded = scene_depth != 1.0
           && anchor_depth > scene_depth + text_depth_bias
```

通常 `1.0` 是清除后的背景，没有表面可遮挡文字。深度越小表示越靠近观察者；如果锚点深度比该像素表面深度大出容差，就初步判为被挡。`text_depth_bias = 2e-5` 允许同表面 CPU 投影与 GPU 光栅化产生的小差异。

正交视图直接采用这个结果。透视视图只有**初判遮挡**时才进入局部补偿。初判可见无需读取 3×3 邻域。

## 6. 透视局部平面补偿

锚点可能位于像素中心之外。同一个三角形的窗口深度在屏幕坐标中是仿射函数，因此中心像素的深度不一定等于锚点处应有的表面深度。

`text_anchor_is_occluded_perspective` 重新检查中心深度；若已可见直接返回。之后：

```text
dx = anchor_screen_x - (pixel_x + 0.5)
dy = anchor_screen_y - (pixel_y + 0.5)
```

像素中心在整数格子中位于 `x+0.5, y+0.5`。`dx,dy` 各位于约 `[-0.5,0.5)`。代码对四个象限 `sx,sy ∈ {-1,+1}` 尝试局部平面。若 `x+2*sx` 或 `y+2*sy` 越界，整个象限跳过。

令 `center` 为中心像素深度，`step_x` 为相邻横向像素深度减中心，`step_y` 同理：

```text
reconstructed = center + step_x × (dx × sx)
                       + step_y × (dy × sy)
```

如果锚点仍比预测表面深度更远，直接检查下一个象限。否则先验证这个候选平面：遍历该象限 3×3 样本，对索引 `i,j` 预测 `center + i*step_x + j*step_y`。只要任何样本为背景 `1.0`，或预测残差超过 `text_depth_plane_tolerance = 2e-6`，该象限失效。某象限全部通过时返回“未遮挡”。四个都失败时保留“遮挡”。

这个过程没有取邻域中最远深度。它要求邻域符合平面关系，避免直接在物体轮廓旁拿背景来放行文字。

## 7. 一组数字算例

中心深度 `0.5000`，向右一像素深度为 `0.5020`，锚点在中心右侧 `0.4` 像素。假设纵向无变化，则候选锚点表面深度为 `0.5000 + 0.0020×0.4 = 0.5008`。

锚点自身深度也为 `0.5008`。原单像素判断会算 `0.5008 > 0.5000 + 0.00002`，于是错误剔除。若 3×3 样本确实满足同一平面，局部重建会允许这条文字显示。

若中心是前景物体 `0.4000`，锚点真实在后方 `0.5008`，轮廓两侧样本深度不符合单一平面，候选会失败，文字保持剔除。复杂几何仍可能出现不能补偿的情况；它并非几何 ID 或真实三角形归属证明。

## 8. `tot`、`IS_CLIPPED` 与 BLF

通过原裁剪和新深度判断的文字使 `tot++`。若 `tot>0`，函数临时关闭视图裁剪距离，调用 `drw_text_cache_draw_ex`。这个函数查看每条 `vos.sco[0]`，只画未被标为 `IS_CLIPPED` 的文字。文字最终由 `BLF_draw_default` 画出。

`vos.xoffs/yoffs` 是文字的二维排版，例如居中或多行间距；遮挡深度使用 `vos.vec` 三维锚点，而不是字符串每个字形覆盖的所有像素。因此“文字的一部分挡住了”与“锚点挡住了”不是同一判定问题。

## 9. 二维视图为什么不同

`v3d == nullptr` 时，函数走 View2D 投影路径，不读取本方案的 3D 场景深度，也不使用透视平面补偿。新标志文档明确限定在 3D 空间绘制时支持。
