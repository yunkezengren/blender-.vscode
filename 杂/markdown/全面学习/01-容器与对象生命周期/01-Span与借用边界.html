02原理、状态与设计取舍

从调用者的问题开始

假设一个函数要计算一组点的包围盒。点可能来自 Vector、固定大小数组，或另一个数组中的一段。函数需要的是可连续访问的元素，不需要决定容量，也不需要释放数据。Span 把这个需求表达成地址与长度，使同一算法能够接收不同所有者的数据。这里的通用性来自缩小接口要求，而不是增加继承层次。

读 BLI_span.hh 时先看构造、size、operator[] 和 slice。对每个操作分别回答：是否复制元素、是否分配、是否延长底层数据寿命。一个切片通常只是新的视图；它的创建便宜，但原数组销毁后它也会失效。把这些语义画在调用栈上，比背下所有成员函数更有价值。

const 限制的是哪一层

Span<T> 提供只读元素访问；MutableSpan<T> 允许修改元素。const MutableSpan<T> 约束视图对象本身，并不自动把其所引用的元素变成只读。这和 const 指针、指向 const 对象的指针之间的区别相似。阅读接口时必须区分视图状态能否变化和目标数据能否变化。

只读访问也不保证没有别名。另一个可写引用仍可能指向同一内存，所以多线程读写需要额外的同步和所有权约束。不要从一个 const 参数推导出整个系统中这份数据永远不变。

用生命周期图判断安全性

把所有者画成长条，把视图画成位于其内部的短条。视图被使用的整个区间都应落在有效存储区间内。Vector 扩容会改变存储位置，即使 Vector 对象还活着，旧 Span 也可能失效。因此检查生命周期时，必须同时追踪所有者寿命与其底层存储的稳定性。

如果函数返回局部 Vector 的 Span，函数退出后会留下悬空视图。更可靠的接口可能让调用者提供目标缓冲区，或者直接返回拥有数据的对象。选择依据是结果需要活多久、谁能负责其销毁。

Span::slice：只改变视图，不复制元素

先把 Span 想成地址与长度这两个元数据。下面是一个完整函数；它返回新的借用视图，不分配内存，也不拥有原数组。读完每一行以后，应能指出谁负责保存底层对象，以及哪一次容器操作会让这个视图悬空。

要求起点非负。BLI_assert 用于检查调用契约，不能把它当作面向不可信输入的运行时校验；关闭断言以后，调用者仍然必须满足前置条件。

BLI_assert(size >= 0);

要求元素数非负。负数若进入后续指针或长度运算，会破坏视图表达的区间模型。

L145
BLI_assert(start + size <= size_ || size == 0);

对于非空切片，要求右端点不超过原视图长度；这里显式允许 size 为零的特殊路径。不要据此推断任意越界 start 都安全：下一行仍然进行指针算术，还必须满足 C++ 的地址运算规则。start + size 的有符号溢出也不是这条断言能修复的问题。

L146
return Span(data_ + start, size);

返回一个新 Span：新首地址向后移动 start 个 T，长度为 size。移动单位是元素而非字节；没有执行 T 的复制构造。新旧视图指向同一批对象，底层容器扩容以后两者都可能失效。

L147
}

结束函数。返回值拥有的是描述信息；它没有获得底层存储的所有权。

用具体输入推演状态

令数组为 [10,20,30,40,50]，slice(1,3) 返回地址 &array[1] 与长度 3，观察结果为 [20,30,40]。若底层是 Vector，随后发生一次实际迁移，原 Span 中的地址不会自动更新。可以把这个反例写成生命周期图，但不要在程序里解引用已失效的视图来“验证”。

调用关系与设计判断

这个接口把“选择区间”和“管理存储”分开。它让函数接受不同容器的数据而不引入复制，但把生命周期责任留给调用者。独立设计时，先写清输入视图在调用期间有效，返回视图是否允许逃逸，以及调用期间是否有人能修改底层容器。

Span 的构造：地址与长度不等于所有权

这是最基础的指针加长度构造器。先逐行明确它没有做的存储管理，再读切片和元素访问，才能避免把 Span 当成安全的拥有容器。

调用关系与设计判断

借用接口的边界校验只能使用已有元数据。真实分配长度、对象生命周期、并发修改者这些事实必须由拥有者与调用协议保证。函数如果保存 Span 到成员中，要在设计说明里直接写出它借用谁。

BLI: new C++ ArrayRef, Vector, Stack, ... data structures

先读 ArrayRef 的设计说明；这个历史名称后来变为 Span。关注为什么它适合作为数组输入参数。

展开提交原文、变更规模与阅读命令
Many generic C++ data structures have been developed in the
functions branch. This commit merges a first chunk of them into
master. The following new data structures are included:

Array: Owns a memory buffer with a fixed size. It is different
  from std::array in that the size is not part of the type.

ArrayRef: References an array owned by someone else. All elements
  in the referenced array are considered to be const. This should
  be the preferred parameter type for functions that take arrays
  as input.

MutableArrayRef: References an array owned by someone else. The
  elements in the referenced array can be changed.

IndexRange: Specifies a continuous range of integers with a start
  and end index.

IntrusiveListBaseWrapper: A utility class that allows iterating
  over ListBase instances where the prev and next pointer are
  stored in the objects directly.

Stack: A stack implemented on top of a vector.

Vector: An array that can grow dynamically.

Allocators: Three allocator types are included that can be used
  by the container types to support different use cases.

The Stack and Vector support small object optimization. So when
the amount of elements in them is below a certain threshold, no
memory allocation is performed.

Additionally, most methods have unit tests.

I'm merging this without normal code review, after I checked the
code roughly with Sergey, and after we talked about it with Brecht.

06自测：先回答，再展开

Span 复制后，元素会复制吗？

通常只复制视图描述；元素仍由原所有者管理。具体构造方式仍应以接口约定为准。

Vector 还活着，Span 就一定安全吗？

不一定，扩容、移除元素或其他改变存储有效性的操作都可能破坏原视图。
