02原理、状态与设计取舍

场景数据不等于可执行任务

一个对象包含变换、几何和其他计算方面。若依赖图只以整个对象为最小单位，就可能过于粗糙；若把所有底层计算完全扁平化，又会失去组织关系。IDNode、ComponentNode、OperationNode 提供不同层次的表达，让数据块、计算组件和具体操作分开。

阅读这三个头文件时记录父子归属与输入输出关系，不要把层级包含关系误认为执行先后。执行顺序由依赖关系决定，组织层级则帮助构建、标记和查询。

构建节点与构建关系

DepsgraphNodeBuilder 负责建立需要的节点，DepsgraphRelationBuilder 负责补充计算约束。两者都要理解场景数据，但输出职责不同。一个节点存在，不代表它在本次更新中一定执行；还需要失效与可见性等判断。

从一个对象受父对象变换影响的简单场景开始，标出读取源、写入目标和需要先完成的操作。先画十个以内的节点，再看真实 builder 如何把这种关系扩展到修改器、驱动和其他对象。

与几何节点图保持边界

场景 Depsgraph 决定场景层面的求值与更新；一个几何节点修改器内部又有自己的 LazyFunction 图和 Field 求值。三者可以嵌套参与工作，但有不同状态、粒度和缓存。不能把某层的优化直接假定存在于另一层。

官方 Depsgraph 设计文档可帮助理解职责，其历史背景较早；当前类名和执行路径应以本地源码为准。本课程的源码卡片提供可直接继续阅读的当前入口。

void evaluate_node(const DepsgraphEvalState *state, OperationNode *operation_node)
{
  blender::Depsgraph *depsgraph = reinterpret_cast<blender::Depsgraph *>(state->graph);

  /* Sanity checks. */
  BLI_assert_msg(!operation_node->is_noop(), "NOOP nodes should not actually be scheduled");
  /* Perform operation. */
  if (state->do_stats) {
    const double start_time = BLI_time_now_seconds();
    operation_node->evaluate(depsgraph);
    operation_node->stats.current_time += BLI_time_now_seconds() - start_time;
  }
  else {
    operation_node->evaluate(depsgraph);
  }

  /* Clear the flag early on, allowing partial updates without re-evaluating the same node multiple
   * times.
   * This is a thread-safe modification as the node's flags are only read for a non-scheduled nodes
   * and this node has been scheduled. */
  operation_node->flag &= ~DEPSOP_FLAG_CLEAR_ON_EVAL;
}

用具体输入推演状态

同一节点两条路径都执行 evaluate，一条额外记录时间。NOOP 节点应在调度阶段直接推动孩子，而不是到这里执行空回调。测量图性能时区分节点累计 CPU 时间与从 refresh 开始到结束的实际耗时。

调用关系与设计判断

沿 OperationNode → ComponentNode → IDNode 找到所属数据块，再回到 relation builder 看先后关系如何建立。结构层次解释“操作属于谁”，关系边解释“操作必须等待谁”，两个维度不能互相替代。

OperationNode 完整定义：结构归属与执行状态逐项拆开

这个完整类型定义把执行回调、归属组件、调度状态和诊断标识集中到一个操作节点。每个字段的更新阶段不同，不能因为都在同一对象里就用同一个“是否完成”状态概括。

struct OperationNode : public Node {
  OperationNode();

  std::string identifier() const override;
  /**
   * Full node identifier, including owner name.
   * used for logging and debug prints.
   */
  std::string full_identifier() const;

  void tag_update(Depsgraph *graph, eUpdateSource source) override;

  bool is_noop() const
  {
    return bool(evaluate) == false;
  }

  OperationNode *get_entry_operation() override
  {
    return this;
  }
  OperationNode *get_exit_operation() override
  {
    return this;
  }

  /* Set this operation as component's entry/exit operation. */
  void set_as_entry();
  void set_as_exit();

  /* Component that contains the operation. */
  ComponentNode *owner;

  /* Callback for operation. */
  DepsEvalOperationCb evaluate;

  /* How many inlinks are we still waiting on before we can be evaluated. */
  uint32_t num_links_pending;
  bool scheduled;

  /* Identifier for the operation being performed. */
  OperationCode opcode;
  int name_tag;

  /* (OperationFlag) extra settings affecting evaluation. */
  int flag;

  DEG_DEPSNODE_DECLARE;
};

用具体输入推演状态

同一个 ID 的 Geometry 组件可以包含多个 OperationNode，它们都拥有同一类结构归属，却可能有不同前置关系。两节点 owner 相同不代表可任意并行；反之不同 ID 的操作也可以有依赖边。

调用关系与设计判断

把 IDNode、ComponentNode、OperationNode 画成树，把 Relation 画成跨节点有向边，再分别记录 flag、pending、scheduled 的状态迁移。层次树解释管理归属，关系图解释执行先后，状态协议解释本轮更新，这三者一起构成 Depsgraph。
