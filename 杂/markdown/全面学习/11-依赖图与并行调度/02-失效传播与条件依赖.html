02原理、状态与设计取舍

脏状态与就绪状态分开

源数据变化后，依赖它的结果可能失效。传播阶段决定哪些操作需要更新；调度阶段判断这些操作的前置依赖是否完成。一个操作可能已脏但暂时不就绪，也可能依赖已满足但本次不需要执行。把二者混成一个布尔量会让逻辑难以维护。

从 deg_eval_flush.cc 追踪更新传播，再到 deg_eval.cc 看执行。教学版本可以用 dirty 与 remaining_dependencies 两个状态表达，真实实现还有更多细节，应保持层次对应而不宣称结构完全相同。

条件本身也可能需要求值

禁用修改器时不必执行其昂贵依赖，看起来简单。但如果启用状态受驱动或动画控制，为了知道它是否禁用，仍需更新决定该状态的数据。条件依赖与被条件控制的值依赖必须区别对待。

f12f7800c29 优化禁用修改器的依赖求值，并包含手动可见性和驱动可见性场景。它适合与你学过的 Switch 对照：二者都涉及条件需求，但分别位于场景图与节点执行图。

验证应观测执行集合

最终画面相同不说明跳过计算正确。记录哪些操作被执行，确认禁用时昂贵工作被跳过，而改变条件时能够恢复执行。再测试条件的动画变化和共享依赖，避免让一个禁用消费者误伤另一个仍需结果的消费者。

递增更新还要处理拓扑关系变化：新增依赖边与源值变化不是同一件事。教学阶段可以在图结构变化时全量重建，先把值变化下的更新协议做对。

调用关系与设计判断

分别画三张状态表：needs_update 说明结果过期，pending parents 说明前置关系是否完成，scheduled 说明当前阶段是否已经安排。重置这些字段的时机与读取时机同样重要，不能只背一个字段名。

等待计数初始化：只等待本轮真正需要的父操作

完整函数说明 num_links_pending 不是静态入度。它只统计当前可见且需要更新的非环操作父关系；已是最新的父节点不应阻塞本轮执行。

void calculate_pending_parents_for_node(const DepsgraphEvalState *state, OperationNode *node)
{
  /* Update counters, applies for both visible and invisible IDs. */
  node->num_links_pending = 0;
  node->scheduled = false;
  /* Invisible IDs requires no pending operations. */
  if (!check_operation_node_visible(state, node)) {
    return;
  }
  /* No need to bother with anything if node is not tagged for update. */
  if ((node->flag & DEPSOP_FLAG_NEEDS_UPDATE) == 0) {
    return;
  }
  for (Relation *rel : node->inlinks) {
    if (rel->from->type == NodeType::OPERATION && (rel->flag & RELATION_FLAG_CYCLIC) == 0) {
      OperationNode *from = static_cast<OperationNode *>(rel->from);
      /* TODO(sergey): This is how old layer system was checking for the
       * calculation, but how is it possible that visible object depends
       * on an invisible? This is something what is prohibited after
       * deg_graph_build_flush_layers(). */
      if (!check_operation_node_visible(state, from)) {
        continue;
      }
      /* No need to wait for operation which is up to date. */
      if ((from->flag & DEPSOP_FLAG_NEEDS_UPDATE) == 0) {
        continue;
      }
      ++node->num_links_pending;
    }
  }
}

调用关系与设计判断

与 flush 阶段对照：needs_update 决定谁过期，pending 决定过期节点何时可执行。条件依赖和可见性变化必须在初始化前被正确反映，否则即使原子递减完全正确，仍会在错误的初始计数上运行。

不能，确定其禁用状态所需的条件，以及其他消费者的需求仍可能要求上游工作。
