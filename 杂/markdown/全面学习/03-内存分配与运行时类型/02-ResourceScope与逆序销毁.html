02原理、状态与设计取舍

运行时也可以有作用域

普通 C++ 大括号里的局部变量按逆序析构。ResourceScope 把类似责任显式化：函数可以把资源交给调用者持有的 scope，让它们在统一时刻销毁。这对于类型、数量都在运行时才确定的执行临时数据尤其有用。

先读类顶部注释，再看怎样登记构造出的对象和外部资源。它与 LinearAllocator 可以配合，但两者承担不同责任：一方组织存储，另一方确保适当的销毁动作发生。

逆序销毁需要依赖约定

如果后创建的 B 借用先创建的 A，按 B、A 的顺序销毁通常符合要求。反过来，若 A 的析构需要访问后创建的 B，这种顺序就不满足依赖。逆序销毁是一项可依赖的规则，不是自动解决任意资源依赖图的算法。

资源登记成功与失败也要推演：构造对象之后、注册清理动作之前若失败，谁负责回收？可靠封装需要让这种间隙得到处理。把这类问题联系到上一模块的容器异常路径，能看到同一模式。

借用结果不能越过 scope

一个函数把临时数组交给 scope 后返回 Span，Span 的有效期受到 scope 约束。如果上层缓存了该 Span，而 scope 已销毁，问题与返回局部数组视图完全相同，只是寿命边界更隐蔽。

阅读 FieldEvaluator 的 scope_ 成员时，可以追踪求值临时数据如何保活。不要通过“成员变量看起来还在”判断返回视图寿命，而应找到具体数据由谁拥有、什么时候销毁。

template<typename T, typename... Args> inline T &ResourceScope::construct(Args &&...args)
{
  destruct_ptr<T> value_ptr = allocator_.construct<T>(std::forward<Args>(args)...);
  T &value_ref = *value_ptr;
  this->add(std::move(value_ptr));
  return value_ref;
}

用具体输入推演状态

构造对象 A 后得到引用 r，scope 保存 A 的析构登记。函数局部 value_ptr 的责任已移走；函数返回时不会把 A 析构。退出 scope 后 A 被析构，此时 r 不再允许使用。将两个相互依赖资源按构造顺序登记，并检查实际释放顺序。

调用关系与设计判断

区分三层：构造 T、登记析构动作、最终释放 allocator 块。自己实现时用事件日志记录 constructor/destructor，并验证登记阶段失败是否泄漏；不要仅凭使用了智能指针就宣称所有异常路径已经正确。

登记析构指针：拥有对象清理，空间仍归 allocator

这是 construct 调用链中必须继续阅读的一层。destruct_ptr 与 unique_ptr 的差别直接体现在回调中：此处只调用析构，不执行 delete。

template<typename T> inline T *ResourceScope::add(destruct_ptr<T> resource)
{
  T *ptr = resource.release();
  if (ptr == nullptr) {
    return nullptr;
  }
  /* There is no need to keep track of such types. */
  if constexpr (std::is_trivially_destructible_v<T>) {
    return ptr;
  }

  this->add(ptr, [](void *data) {
    T *typed_data = reinterpret_cast<T *>(data);
    typed_data->~T();
  });
  return ptr;
}

用具体输入推演状态

allocator 块中构造一个 std::string，登记后退出 scope 会调用 string 析构，随后 allocator 的整块空间释放。若把 typed_data->~T() 换成 delete typed_data，就可能把线性块内部地址错误交给普通 delete。

调用关系与设计判断

把 add(unique_ptr<T>)、add(shared_ptr<T>) 与此函数对照：第一种需要 delete，第二种释放一份共享引用，这一种只析构。相同的 void* userdata 并不代表相同的释放协议。

逆序释放的完整实现：分配器必须最后退出

从登记过程走到真正析构。资源列表是 ChunkedList，源码约定其迭代顺序为构造逆序；这里不是先把列表反转，再向前遍历。

ResourceScope::~ResourceScope()
{
  /* Frees all resources in reverse order of construction. Note that #ChunkedList always iterates
   * in reverse order. */
  LinearAllocator<> *used_allocator = &allocator_;
  for (ResourceData &resource : resources_) {
    void *data = resource.data;
    resource.free(data);
    if (data == used_allocator) {
      break;
    }
  }
}

BLI: optimize memory usage in ResourceScope

关注作用域记录本身也有内存成本，优化应保持销毁语义。

展开提交原文、变更规模与阅读命令
This implements multiple improvements for the `ResourceScope` utility:
* Instead of a `Vector` it uses a `ChunkedList` to keep track of resources. This
  is has less memory overhead and does not require reallocations when growing.
* One can pass an already existing `LinearAllocator` to a constructor instead of
  always creating a new one.
* New constructors that allow providing initial memory for the resource scope
  (e.g. a large buffer on the stack).
* If it creates a new allocator, it increases the initial allocation size and
  uses the extra bytes as buffer in the allocator. This is instead of allocating
  twice.
* The size of `ResourceScope` shrinks from 176 bytes to just 16 bytes (although
  it does use more when it has to create a new allocator).

06自测：先回答，再展开

逆序销毁是否等于拓扑排序？

不等于；它依赖资源按满足约束的顺序登记，不会推断任意依赖图。

scope 可以替代所有 shared_ptr 吗？

不能；scope 适合统一寿命，独立延长寿命的对象可能需要其他所有权模型。
