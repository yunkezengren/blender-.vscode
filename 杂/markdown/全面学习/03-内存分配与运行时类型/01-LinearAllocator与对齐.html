02原理、状态与设计取舍

共同寿命带来的简化

如果一批节点执行数据都在本次求值结束后销毁，就不一定需要为每个小块分别向通用堆申请与归还。线性分配器在较大缓冲区中推进游标，缓冲区不够时再获得新的块。其速度来自对释放模式的限制：它适合成批释放，不提供任意顺序的细粒度回收。

把数据寿命画成时间条。如果大量对象的结束时间近似一致，分区分配可能有效；如果少数长期对象不断夹在短命对象中，整块内存就可能长期无法回收。选择分配器应从寿命分布开始。

对齐是正确性条件

假设游标为 p，对齐要求为正的二次幂 a，常见上取整公式是 (p+a-1)&~(a-1)。必须检查加法溢出、剩余容量和分配器支持的对齐上限。公式只是教学模型；真正实现还需要处理大分配和新块路径。

对齐填充不是有效载荷，但仍占用缓冲区。记录 requested bytes、padding 和实际获得的块大小，才能解释小对象工作负载的内存利用率。大量不同对齐需求也会改变浪费比例。

稳定地址与对象构造分开

追加新的缓冲块通常可以保留旧块地址，这适合图节点和临时结构相互引用。但 allocator 的寿命必须覆盖这些引用的使用区间。其 NonMovable 等约束也值得阅读，理解哪些简化来自对象本身不移动。

返回原始内存与提供 construct<T> 是不同层次。即使有构造辅助函数，也不能推断分配器自动追踪所有对象的析构；这正是下一课 ResourceScope 要补充的问题。

  void *allocate(const int64_t size, const int64_t alignment)
  {
    BLI_assert(size >= 0);
    BLI_assert(alignment >= 1);
    BLI_assert(is_power_of_2(alignment));

    const uintptr_t alignment_mask = alignment - 1;
    const uintptr_t potential_allocation_begin = (current_begin_ + alignment_mask) &
                                                 ~alignment_mask;
    const uintptr_t potential_allocation_end = potential_allocation_begin + size;

    if (potential_allocation_end <= current_end_) {
#ifdef BLI_DEBUG_LINEAR_ALLOCATOR_SIZE
      user_requested_size_ += size;
#endif
      current_begin_ = potential_allocation_end;
      return reinterpret_cast<void *>(potential_allocation_begin);
    }
    if (size <= large_buffer_threshold) {
      this->allocate_new_buffer(size + alignment, alignment);
      return this->allocate(size, alignment);
    }
#ifdef BLI_DEBUG_LINEAR_ALLOCATOR_SIZE
    user_requested_size_ += size;
#endif
    return this->allocator_large_buffer(size, alignment);
  };

调用关系与设计判断

每次 allocate 的局部正确性依赖当前块地址边界有效，跨块正确性依赖 owned_buffers_ 保留旧块。不能在换块时释放仍被用户引用的旧分配。对齐测试、跨块存活测试与特大块测试覆盖的是三种不同责任。

06自测：先回答，再展开

线性分配为什么不适合任意释放？

它通过省略每块独立回收管理来简化路径，寿命不一致会留下不能及时回收的空间。

释放整块内存会调用字符串析构吗？

不会自动由原始内存释放完成，必须有对象层的析构管理。
