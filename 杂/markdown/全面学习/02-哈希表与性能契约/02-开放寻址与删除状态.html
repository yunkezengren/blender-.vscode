02原理、状态与设计取舍

查找需要一个可靠的停止条件

教学版本采用线性探测：从哈希决定的槽位开始，遇到碰撞就检查后续位置。发现真正的空槽可以停止，因为按插入规则，目标键若存在就不会越过这个从未被占用的停止点。这个结论依赖于插入和查找采用一致的探测规则。Blender 的具体探测策略应从实现中读取，不要把教学线性探测直接当成其当前实现。

假设 A 与 B 的起始槽相同，A 在槽 2，B 在槽 3。删除 A 后把槽 2 变为普通空槽，查找 B 会提前停止。因此删除需要保留探测链的信息，常见做法是留下 Removed 状态。

逻辑大小与探测压力不同

size 只统计有效元素。已经移除的槽位虽然没有键值，仍可能延长查找路径。于是相同 size 的两张表可能有不同的查找成本。理解 Map 时应同时关注有效槽数量、已用或移除槽数量、总容量以及触发重建的条件。

BLI_map_slots.hh 将槽位管理从高层 Map 逻辑中分离。阅读时检查槽位从空到占用、占用到移除的转换，确认键和值在哪一步构造和析构。模板化槽位也可能允许不同存储策略，不应假定所有键类型占用相同元数据。

接口帮助调用者表达前提

lookup、lookup_ptr、lookup_or_add、add_new 等接口往往有不同前提和失败表达。一个宣称键一定存在的接口，可以省去调用者重复判断，但需要调试断言或清楚约定。选择接口时先判断你的知识：已知存在、可能不存在，还是需要查找并插入。

返回的值指针也受重建影响。把 Map 中值的地址长期缓存到其他系统里，会把表的内部移动变成上层隐患；如需稳定身份，应明确使用单独所有权或间接句柄。

用具体输入推演状态

A、B 有同样的初始桶，A 占槽 3，B 因碰撞占槽 4。删除 A 后槽 3 变 removed；查 B 时在槽 3 不命中也不终止，继续到槽 4。若删除直接设 empty，查询会在槽 3 返回 nullptr。

调用关系与设计判断

这个反例应成为删除测试。再测试缺失键与一长串墓碑，记录探测次数，并对照 ensure_can_add 的重建条件。正确性由状态机保证，性能由墓碑清理与负载策略共同保证。

重建槽位：新表为什么必须重新探测

完整辅助函数展示占用槽怎样进入新表。它不是把旧槽数组按原下标复制过去：掩码变化后，初始桶和碰撞路径都会变化。此处处理的是重建阶段，删除标记如何影响普通查找还要与槽位状态接口一起阅读。

用具体输入推演状态

假设旧表有 8 个槽，新表有 16 个槽。同一哈希与掩码相与后的初始位置可能改变。旧表某槽之前有墓碑，新表只重插有效项，因此墓碑不会随键一起继承。使用多个初始桶相同的键可以验证碰撞处理。

调用关系与设计判断

把普通查找的“空槽终止、删除槽继续”与重建的“寻找新空槽”分开。只理解重建不能证明删除正确；需要构造 A、B 碰撞，删除 A 后仍能找到 B 的例子，沿 lookup_slot__impl 逐个检查状态。

HISTORY b242c618450 Jacques Lucke · 2025-12-12

Fix: BLI: bad performance edge case in hash table implementations

先理解删除留下的历史信息，再进入重建策略的性能修复。

展开提交原文、变更规模与阅读命令
The issue happened when the hash table (e.g. Map) has close to a power of two
number of elements and repeatedly deletes and adds values. In this case the map
is rebuild more often than is necessary, and in the worst case a rebuild happens
each time something is removed and added again.

The fix here is to make sure that each call to `realloc_and_reinsert` is
actually worth it by making it grow the map in some cases where it previously
wouldn't. A similar optimization already exists in
`Vector::realloc_to_at_least`.

An alternative would be to support overriding removed-slots in `Map::add`, but
that has negative performance implications for the most common case when no
elements are ever removed.

This brings back performance to the same level before #150009:
`60k_cubes_same_mesh.blend: old: 11.3s, main: 70s, this patch: 11.3s`

06自测：先回答，再展开

Removed 与 Empty 都没有值，为什么不同？

Removed 保留了探测链不能中断的信息，Empty 可以作为查找停止点。

size 相同，性能就接近吗？

不一定，删除历史、负载、碰撞分布和探测长度都影响实际成本。
